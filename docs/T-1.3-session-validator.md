# T-1.3 — ERC-7579 session-key validator

Status as of 2026-11-16: implemented and tested locally. Not deployed or installed; the installation transaction needs T-1.1 (account and factory on Base Sepolia).

## What exists

- `contracts/FrostSessionValidator.sol`: a Type 1 validator module (`isModuleType(1)` only). Interfaces follow the ERC-7579 and ERC-4337 text in `specs/` (`contracts/interfaces/`).
- Key storage is per account, keyed by `msg.sender`, so one account cannot use another account's key. The key is stored as two fixed fields (`uint8 prefix`, `uint256 x`) in a mapping, so both slots sit at `keccak(account‖index)+0` and `+1`, inside the "associated storage" range that ERC-7562 rule STO-021 allows an account's validation to read. A first layout using dynamic `bytes` put the key data at a hashed slot outside that range; tests now assert the slot positions and that nothing is stored at the hashed slot.
- `onInstall(data)`: `data` is 45 bytes: the 33-byte compressed group public key, then `validAfter` (6 bytes) and `validUntil` (6 bytes), packed. It reverts with `InvalidInstallData` for any other length, `InvalidSessionPublicKey` unless the key is well formed, has a non-zero x below the group order and is on the curve (the check T-1.8 left for this task), `InvalidSessionWindow` unless `validUntil` is above both `validAfter` and the current block time (a session without an end time is rejected), and `SessionAlreadyInstalled` if a key is already set. The prefix and both times share one storage slot and `x` takes the second, so the ERC-7562 layout is kept.
- `onUninstall`: deletes the key and never reverts, so revocation cannot be blocked.
- `validateUserOp`: `userOp.signature` is the 65-byte RFC 9591 encoding `R || z`, and the signed message is the raw 32-byte `userOpHash`. The enclave side must sign exactly those bytes. On success it returns the packed `validationData` with `validUntil` and `validAfter` and a zero authorizer, so the EntryPoint enforces the clock (the validator reads no timestamp, which ERC-7562 bans). It returns 1 (`SIG_VALIDATION_FAILED`) without reverting on any failure: no key installed, wrong length, bad signature.

## Decisions to review

1. **ERC-1271 never authorizes the session key.** `isValidSignatureWithSender` always returns `0xffffffff`. The spec says to return the magic value when a signature is valid, but forwarding it would let the agent's session key sign permits and off-chain orders outside any spend policy (invariant I-3). Under this definition no ERC-1271 signature is valid. If you want it forwarded, that is a policy change for T-2.1.
2. **Policy scope (decided 2026-11-16, D1 of `docs/local-pipeline-plan.md`).** T-1.3 enforces the TTL only, which costs no measurable gas. The per-asset cap, allowlist and 24-hour window go in the T-2.2 policy hook, not the validator. This amends T-2.1's wording, which lists them under the validator.

## Verification (local, Foundry 1.9.0, solc 0.8.28, cancun)

- 42 Solidity tests pass: 15 for the library, 23 for the validator (including the validity window) and 4 smoke tests for the etched EntryPoint.
- Acceptance criteria: a signature from each 2-of-3 quorum ({1,2}, {1,3}, {2,3}) is accepted; a below-threshold signature (one signature share) and a lone enclave signing with its own key share are both rejected.
- The quorum, below-threshold and lone-enclave vectors were produced from the T-1.6 Python reference using the RFC 9591 E.5 key shares, so they are consistent with that reference, not independent of it.
- Gas through the test harness: `validateUserOp` about 17.5k for a valid signature, unchanged by the TTL (storage reads were warm because the key was installed in the same test transaction); first `onInstall` about 74.8k; `onUninstall` about 27k to 33k.

# T-2.2 — policy hook for session operations

2026-11-17. `contracts/FintechPolicyHook.sol` (ERC-7579 type 4) plus a structural change to `FintechModularAccount`. Scope is the session authority gap recorded in `docs/T-1.1-account-and-factory.md` risk 1 and `docs/step-9-revocation-paymaster-recovery.md`. Everything is local; nothing was run on Base Sepolia.

## What changed in practice

A quorum-signed session operation can no longer install or uninstall modules, call the account itself, use the delegatecall mode, call a target outside the allowlist, or spend more than the per-asset cap in any rolling 24 hours. A compromised session quorum is now limited to what the owner allowlisted and capped.

## Design decisions (please review)

These were not fixed by the roadmap. I chose the simplest option that is sound.

1. **The account, not the hook, tells session operations from owner operations.** The hook only sees `msg.sender` (always the EntryPoint) and `msg.data`, so it cannot tell who signed. The EntryPoint v0.8.0 deployed on Base Sepolia has no `getCurrentUserOpHash` (the selector is absent from the runtime code in `fixtures/`; `getUserOpHash` is present), so the account cannot look up which validator approved the running operation either. Instead the account gives session operations their own entry point, `executeAsSession(bytes32,bytes)`, which only the EntryPoint can call and which fails when no hook is installed. In `_validateUserOp`, an operation whose nonce key names an installed validator module must have `executeAsSession` as its call data selector, otherwise validation returns `SIG_VALIDATION_FAILED` (`AA24`). The quorum signature covers the call data, so the selector cannot be swapped afterwards.
2. **Every installed validator module is session class.** The owner path is the account's native ECDSA signer. A validator module installed later (for example a passkey) would also be limited to `executeAsSession`. If an owner-equivalent module is ever wanted, this rule needs a deliberate exception.
3. **The hook polices only `executeAsSession`.** Owner operations, executor modules (social recovery) and module install or uninstall pass through untouched, so a faulty policy cannot stop the owner from uninstalling the hook or the session validator (the "bricking" risk in A-5, and I-2).
4. **Parsing is done once, by the same code the account uses.** `preCheck` calls `resolveExecutions` on itself with the original call data, so the outer ABI decoding is the compiler's own, and the inner decoding uses `ERC7579Utils.decodeSingle` and `decodeBatch`, the helpers the account executes with. Tests execute a non-canonical outer and a non-canonical batch encoding and check the counted value equals the value that moved.
5. **Policy.** Allowed call types: single and batch with the default execution type, zero mode selector and payload (anything else is `UnsupportedMode`). At most 16 calls per batch. Target must be an allowlisted contract or a capped ERC-20; never the account, the hook, the EntryPoint or the zero address. Native value on an allowlisted target counts against the native cap (asset `address(0)`). A capped ERC-20 accepts only `transfer(address,uint256)` and `approve(address,uint256)` with exact 68-byte call data and no native value; the amount counts against that token's cap (approvals count too, so they cannot create unbounded spending authority). Caps are nominal per asset, as ADR-005 decided; no USD conversion.
6. **Rolling window.** Spends are kept as `(timestamp, amount)` events, at most 32 live per asset; events at least 24 hours old stop counting at that exact second. Spends in the same second merge into one event. When 32 distinct-second events are live the next spend is refused (`WindowFull`) instead of forgetting an old one. Accounting happens in `preCheck`; if the execution reverts, the EntryPoint reverts it with the rest.
7. **`postCheck` is an account-balance check.** For every capped asset, the account's balance may not drop by more than the transfers and native value declared in the same operation. This catches a trusted target pulling tokens through an existing allowance (tested).
8. **Lifecycle.** `onInstall` takes `abi.encode(address[] targets, (address asset, uint256 cap)[] rules)`. Policy is per account and changed only by the account itself (`allowTarget`, `revokeTarget`, `setCap`, where cap 0 removes an asset), which in practice means an owner-signed operation. `onUninstall` only bumps a per-account epoch, so it cannot revert and clears the whole policy and the window in constant gas. Up to 8 capped assets.

## Mapping to the roadmap defects it remediates

| Defect | Remediation |
|---|---|
| A-2 fixed-offset target | Target and value come from the decoded ERC-7579 mode and execution calldata |
| A-3 allowlist skipped when parsing fails | Parsing failure reverts; the zero address is forbidden, not skipped |
| A-4 `postCheck` read the hook's own balance and could underflow | Reads the account's balances with a non-underflowing comparison |
| A-5 no module lifecycle | `onInstall`, `onUninstall` (cannot revert), `isModuleType`, `isInitialized` |

## Evidence

- Forge: 141 tests pass (52 new for the hook, 5 new for the account, existing suites updated to the new session entry point; the fixed session signature in `test/FintechModularAccount.t.sol` was regenerated with `scripts/sign_session_hash.py`). `forge fmt --check` clean.
- Mutation checks, each caught by at least one test and reverted: removing the selector gate in the account; removing the balance-drop comparison; changing the window boundary from `<=` to `<`; counting transfers as undeclared.
- Drill (`scripts\run-local-drill.ps1`), now 17 checks, passed on two consecutive runs: the hook is installed by an owner operation; the quorum ping runs through the hook; a quorum-signed operation using plain `execute` is rejected with `AA24`; a quorum-signed session operation that tries to uninstall its own validator is included, refused by the hook, and the validator stays installed; 0.6 ETH is sent, a further 0.5 ETH is refused (nonce consumed, nothing moved), and the remaining 0.4 ETH passes, so the window adds up to exactly the 1 ETH cap. The previous 13 checks, including I-2 revocation and I-7 recovery, still pass. I also removed the hook's target restrictions temporarily and confirmed the self-call check then fails.
- Python: 192 tests pass, ruff, ruff format and mypy `--strict` clean.

Gas, measured in Forge (not on chain, and warm versus cold storage depends on order): a plain hooked `execute` of the ping cost about 68k, `executeAsSession` of the same ping about 79k, a first native spend about 130k, a later token transfer about 91k. The hook adds nothing to validation gas; the selector gate adds one extra warm read of the installed validator set, since the account already reads it.

## Risks and limits

- **Allowlisted targets are trusted with any calldata.** The hook cannot know what a target does with the account's approvals or funds beyond the tracked assets. Tokens without a cap are not balance-checked. Keep the allowlist short and prefer capped tokens.
- **Token recipients are not restricted.** A session can send a capped token to any address, within the cap. A recipient allowlist is not in the plan; add it if the use case needs it.
- **No slippage or sandwich detection beyond the balance bound.** Minimum-received checks need the trade intent or a price source (T-2.3 and later). The sanctions oracle (T-2.3) is now built into the hook (`docs/T-2.3-sanctions-screening.md`). The ERC-7484 install gate (T-2.4) now exists, so the hook itself must be attested before it can be installed (`docs/T-2.4-module-registry-and-install-gate.md`).
- **Executor modules are not policed.** Calls through `executeFromExecutor` are trusted because the owner installed the module.
- **Uninstalling and reinstalling the hook resets the policy and the window.** Only the owner can do it, and it is the intended way to change policy shape, but it does reset spent-so-far.
- **The 32-event window can lock the session out** until older spends expire, if many distinct-second small spends are made. It fails closed.
- **ERC-7562.** The new validation-time read is storage of the account itself, which the rules allow, but a rule-enforcing bundler was not used (safe mode is off locally).
- **The hook and the changed account are unaudited.** OpenZeppelin's `AccountERC7579Hooked` is a draft contract that its own comments describe as reentrancy sensitive; the hook only reads state and writes its own per-account storage.
- **Caps and allowlist are only as good as the owner's configuration.** Nothing prevents an owner from allowlisting a dangerous target or setting a huge cap.
- **Enclave-side re-validation (T-2.1's second half) now exists** (`docs/T-2.1-enclave-revalidation.md`): the enclaves refuse operations outside the policy before signing. The on-chain hook is still the authority if the enclaves are compromised.

## Update (T-5.2)

The honest statement above — that an allowlisted target can be called with any function and any data, and that a capped token accepts `transfer` and `approve` alike — now holds only for a scope that is **not** payments-only. A payments-only scope refuses call data, refuses `approve`, and refuses any payee that the user has not approved. See `docs/T-5.2-payment-guardrails.md`.

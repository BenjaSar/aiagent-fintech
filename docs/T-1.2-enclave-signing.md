## Update (T-2.1)

The enclaves no longer sign a bare hash. They recompute the operation hash and validate the operation against a sealed session policy before releasing a share; `scripts/sign_with_local_enclaves.py` was removed for that reason. See `docs/T-2.1-enclave-revalidation.md`.

## Behaviour that is enforced and tested

- **Nonces are single use.** The enclave removes the nonces from its pending table before it validates the package, so a rejected or malicious package still burns them. Signing the same session twice, or after `release`, is refused.
- **The enclave refuses** a package for another group key, with fewer signers than the threshold, with a message that is not 32 bytes, or that does not contain this enclave's own commitments.
- **Pending sessions are capped at 32**; the oldest is evicted, which only loses unused nonces.
- **The coordinator verifies every share** against the verifying share it holds from key generation (never the one a reply carries), names the culprit, then aggregates, and the aggregate self-verifies.
- **Fail-closed (I-8).** Fewer than the threshold of attested, reachable enclaves raises `QuorumUnavailableError`; nothing is signed. After any abort the coordinator releases the nonces it created.
- **Only the threshold is contacted**, in ascending identifier order; the rest see no traffic.
- **Attestation gate.** Evidence must carry the expected identity and this session's challenge. `VERIFIED` is accepted; `SIMULATED` only when `allow_simulated_attestation` is true; `REJECTED` never. The dev adapter always reports `SIMULATED`.
- **Real processes.** Three separate Python processes sign; one stopped still signs; two stopped halt signing (tests and a manual run of the scripts).
- **Shares never appear in plaintext on disk**; provisioning refuses to overwrite existing keys.

## Limits to keep in mind

- **A local process is not a TEE.** DPAPI user-scope protects the files from other Windows users and from offline disk theft, not from another process of the same user, which can unseal them. The bearer token blocks browser and accidental requests to localhost, not a same-user attacker.
- **Provisioning still uses the trusted dealer** (`provision_local_enclaves.py`): the provisioning process sees the full key once. The DKG exists as domain code but is not yet run through the enclaves.
- **The enclave signs any 32-byte hash** the authenticated coordinator sends. Spend caps, allowlists and the policy hook (T-2.2) are not here; the enclave cannot yet tell what the hash commits to.
- **Single-threaded server**, so requests to one enclave are serialised; the nonce table needs no lock. Throughput and latency (R-MET-3) are not measured.
- **Nonces live only in memory.** A restarted enclave loses its pending sessions, which fails the session and is safe.
- The wire format is project-defined and unauthenticated beyond the shared token.

## Distributed key generation through the enclaves

Added after the signing path, with `cryptography` 50.0.2 pinned in `pyproject.toml` and `requirements-dev.txt` (it brings `cffi` and `pycparser`).

| Piece | Where | Role |
|---|---|---|
| `DkgEnclave` | `application/dkg_enclave.py` | One participant: begin (part 1), produce sealed round two (part 2), finish (part 3, held pending), confirm (seals the share) |
| `RunKeyGeneration` | `application/run_key_generation.py` | Relays messages, checks every enclave derived the same group key, then asks each to confirm; aborts and abandons otherwise |
| `EnclaveService` | `application/enclave_service.py` | One process object holding the ceremony enclave and, once a share exists, the signer; the HTTP routes call it |
| `X25519ChaChaChannel` | `adapters/x25519_channel.py` | Round-two confidentiality and sender authentication |
| Scripts | `provision_local_enclaves.py --identities-only`, `generate_local_key.py` | Seal identities and roster, then run the ceremony over the running processes |

How the channel works: each enclave has a long-term X25519 identity key sealed in its own folder, and a sealed roster of every participant's public key (the enclave trusts the roster, not the coordinator). Each message uses a fresh ephemeral key; the AEAD key (ChaCha20-Poly1305) is derived with HKDF from the ephemeral-to-receiver and sender-to-receiver Diffie-Hellman results plus all three public keys. The sender is authenticated by the static-static term, and the ephemeral term gives the sender forward secrecy.

**The round one echo check is cryptographic.** The associated data of every round two message includes the ceremony id, sender, receiver and the SHA-256 digest of the round one transcript the sender saw. A receiver with a different view cannot open the message, so a coordinator that shows different participants different round one packages cannot hide it by lying about agreement. Mutation check: removing the digest from the associated data made the dedicated test fail; reverted.

**Two phases.** `finish` derives the share but keeps it in memory; only `confirm`, called after the coordinator saw all enclaves agree, seals it. A protocol failure therefore leaves no enclave holding a share (tested for tampering, equivocation, disagreement and an unreachable enclave). A crash between two confirm calls could still leave a partial set; that is a restart-the-ceremony situation, not a protocol hole. An enclave holding a share refuses to start a ceremony.

Tests: 14 ceremony tests in-process (success, signing with the generated key, tampered package, forked round one view, disagreeing group keys, unreachable enclave, existing share, wrong participant count or threshold, confirmation of a wrong key, unknown ceremony, signing refused before a key exists), 7 channel tests, and 3 multi-process tests (ceremony then signing, restart reloads the share from DPAPI storage, a second ceremony refused). A manual run of the scripts also worked: identities sealed, three processes, key generated, signature produced, second ceremony refused.

## Remaining limits

- The roster is generated by the provisioning script, which sees every identity private key once (they are not FROST secrets). A real deployment would have each enclave generate its key and publish the public part, with the roster pinned through attestation.
- The DKG challenge hash is project-defined (see `docs/T-1.2-dkg.md`).
- `confirm` is not atomic across processes.
- Round two messages carry the sealed share over localhost HTTP with a bearer token; the confidentiality comes from the channel, not from HTTP.
- Session-key rotation (T-2.7) and any DKG performance measurement are not done.

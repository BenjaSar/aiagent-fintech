# T-2.3 — sanctions screening in the policy hook

2026-11-17. `FintechPolicyHook` now screens every counterparty of a session execution against a sanctions oracle and fails closed. Scope is R-P2-2 as restored by ADR-005 §3 (registry #1, the sanctions oracle on the `preCheck` hot path). Everything is local; the oracle is a development contract and nothing was run on Base Sepolia.

## What changed in practice

A session operation (`executeAsSession`) is refused if any execution targets an address the oracle lists, if a capped token call names a listed recipient or spender, or if the oracle cannot give a clear answer. The whole transaction reverts, so nothing executes and the rolling window is not charged. Owner operations, executor modules and module install or uninstall are not screened, so an oracle outage can never stop the owner from revoking the session key or uninstalling the hook (I-2, and `onUninstall` still cannot revert).

## Design decisions (please review)

These were not fixed by the plan. ADR-005 says only "on-chain oracle checks the destination against sanctions blacklists, fail closed", and no provider is named (IG-13).

1. **The interface is one function: `isSanctioned(address) returns (bool)`** (`contracts/interfaces/ISanctionsOracle.sol`). I chose the narrowest shape, and as far as I recall it matches the on-chain sanctions oracle that Chainalysis publishes, but I did not fetch its documentation in this session, so confirm the signature and the deployed addresses before choosing a provider.
2. **The oracle is an immutable of the hook, set in the constructor and required to have code.** It is shared by all accounts, so no owner or session can point an account at an oracle that approves everything, and nothing can switch screening off. The cost is that changing the oracle needs a new hook deployment, which for an account means an owner-signed uninstall and a new install, and the new hook must be attested first (T-2.4).
3. **What is screened.** In `preCheck`, for every execution of a session operation: the target, always (allowlisted targets, capped tokens, anything); and for a capped token `transfer` or `approve`, the recipient or spender named in the call data. Native value goes to the target, so it is covered by the target check. A token call whose address word has dirty upper bits is now refused (`UnsupportedTokenCall`), so the address that is screened is the address the token will use.
4. **Fail closed means every unclear answer reverts.**
   - The oracle reverts, reverts with no data, or runs out of the 150,000 gas it is given: `OracleUnavailable`.
   - The oracle returns nothing, returns a value that is not 0 or 1, or has no code at the time of the call: the call reverts in the hook's own decoding or code-size check. This is also a revert, with a generic reason instead of `OracleUnavailable`. I left it that way rather than adding assembly.
   - The oracle says `true`: `SanctionedAddress(counterparty)`.
5. **The gas given to the oracle is capped at 150,000.** An oracle that burns all gas then costs the operation at most that much, and the operation is refused. The figure is a guess, not measured against a real provider.
6. **The check order inside an execution is: forbidden infrastructure, sanctions, allowlist.** A listed address is therefore reported as sanctioned even if it is also not allowlisted.
7. **The enclaves do not screen.** An enclave has no chain access, and a list copied into its policy would be stale and give false assurance. Enclave-side re-validation (T-2.1) is unchanged; the hook on chain is the only screen. The drill shows exactly this case: an operation the enclaves sign is refused on chain once its target is listed.

## Mapping to the plan

| Item | Remediation |
|---|---|
| T-2.3 "sanctions oracle in `preCheck`, fail closed on unavailability" | Done in the hook; sanctioned-address and oracle-outage cases revert |
| Phase 2 gate: "sanctioned counterparty, oracle outage" negative cases revert | Covered by Forge tests and two drill checks |
| ADR-005 §3: "oracle unavailable ⇒ revert, never permit" | `OracleUnavailable` and the generic reverts above |
| `onUninstall` succeeds under all states | Tested during an oracle outage |

## Evidence

- Forge: 204 tests pass (19 new). `forge fmt --check` clean. New tests cover a listed allowlisted target (native value and a plain call, with nothing executed and the window uncharged), listing and delisting taking effect immediately, a listed token recipient, a listed approval spender, a listed token contract, one listed execution refusing a whole batch, an unlisted recipient unaffected by a listed one, reporting order, a dirty address word, an outage (with the window uncharged and recovery afterwards), an oracle that burns its gas, reverts silently, answers `2`, answers with nothing or has no code, owner operations during an outage, uninstalling the hook during an outage, and the constructor refusing an oracle without code.
- Mutation checks, each caught by at least one test and then reverted: removing the target screening; removing the recipient screening; letting an outage pass (`catch {}`); ignoring the oracle's answer; accepting a dirty address word; accepting an oracle without code.
- Drill (`scripts\run-local-drill.ps1`), now 24 checks, two consecutive runs: an allowlisted target that the oracle lists is refused on chain although the enclaves signed the operation (the operation is included, nothing executes), and after delisting the same kind of operation executes; with the oracle unavailable a session operation is refused, an owner operation still executes, and the session operation executes again when the oracle is back. The earlier 22 checks still pass. With the hook changed to let an outage pass, the drill fails at "an unavailable sanctions oracle fails closed" (`the call executed although it was refused`).
- Python: 281 tests, ruff, ruff format and mypy `--strict` clean (no Python behaviour changed except the drill and its toolbox).

## Risks and limits

- **No provider is chosen (IG-13).** The development oracle has open setters and proves the mechanism only. A real list is only as good and as fresh as its provider; screening an address is not the same as screening a beneficiary or a chain of transfers behind a contract.
- **The hook screens addresses the call names, not what a target does with them.** An allowlisted target that forwards funds to a listed address is not caught; neither is a transfer routed through an intermediary. This is the same trust placed in allowlisted targets in T-2.2.
- **Only session operations are screened.** The owner can send to a listed address. That is deliberate (I-2) and means the user, not the agent, carries that responsibility.
- **Staleness and latency.** A newly listed address is blocked as soon as the oracle lists it, and not before. The oracle call adds two external calls to a token transfer and one to other executions; gas was not measured, and the 150,000 gas cap was not tuned (T-1.8, T-V1). The check runs in the execution phase, so it does not touch the signing latency budget of R-MET-3 and is outside the ERC-7562 validation rules.
- **A hook deployment is tied to one oracle.** If the provider changes its address, every account needs the hook replaced by an owner operation, and each new hook must be attested.
- **Generic reverts for some malformed answers.** Operators see a raw revert rather than `OracleUnavailable` when the oracle returns garbage or has no code.
- **Hook and registry remain unaudited,** and the dev oracle must never be deployed outside local use.

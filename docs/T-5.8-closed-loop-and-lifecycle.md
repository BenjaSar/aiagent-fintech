# T-5.8 — the closed loop and the lifecycle

2026-11-21. Eighth task of the agent-factory program (`docs/agent-factory-program-plan.md`). An agent now has a **life**: it is generated, judged, iterated inside a bounded budget, approved, activated, renewed on schedule and finally torn down — and at no point in that life can the system widen its own authority. No contract changed.

## What changed in practice

**A state machine every agent passes through** (`application/agent_lifecycle.py`). Six states — generated, evaluated, approved, active, refused, retired — and one table of allowed moves. Nothing else can move an agent: skipping the approval, re-approving a retired agent or iterating one that has not been refused all raise. The standing it keeps per agent is the state, the attempts used, the cost spent and the definition in force.

**The monotonic rule, as a comparison on definitions** (`domain/authority_order.py`). `widenings(change)` returns, in plain text, every way a following definition holds more authority than the previous one: an added payee, an added asset, a raised cap, an added **paying** tool, a longer session, any change of rolling window, a raised risk tier, a raised budget, a changed owner. Nothing in the automatic path may produce a non-empty list.

> An added **reading** tool is not a widening. The tool catalog already separates `ToolKind.READ` from `ToolKind.PAYMENT`, and the loop's whole purpose is to let a candidate gain the tool it was missing — `get_payment_status` — without gaining the ability to move more money. Only paying tools are authority.

**The closed loop** (`application/agent_development.py`). Generate, judge, and while the report fails: record the refusal, hand the failures back as feedback, generate again, and check the new candidate against the previous one. The loop ends in one of three ways: a candidate accepted, the attempt budget exhausted, or an iteration that would widen authority. The last two are **escalations**: the outcome carries no candidate and the reason in words, which is what a human is shown. The loop is the live path — `FleetProvisioning` now provisions through it, so the drill's agents are developed, not merely generated.

**Cost control on two levels.** T-5.6 caps the cost of one generation (250,000 micros). The lifecycle caps the cost of a whole development loop (500,000 micros by default) and the number of attempts (3), so a loop cannot pay for progress it is not making.

**An expiry scheduler** (`application/session_schedule.py`). `due_for_renewal` names the agents whose session ends within the lead; `renewal_of` builds the renewal — the same definition with its window moved forward by the same length — and refuses to return anything that is not a renewal by the rule above.

**Unattended renewal through the T-2.7 ceremony.** `FleetProvisioning.renew_agent` derives the renewal's policy, runs the existing `RotateSession` with a fresh DKG, an `UnattendedRenewalApproval` in place of the human, and the previous enclave set retired at the end. The new key, its window and a fingerprint over (renewed definition digest, renewed policy digest, new key) are written to the provenance chain as a `RENEWED` entry whose approver is `scheduler`, not the owner.

**Allowance teardown** (`application/agent_retirement.py`). `RetireAgent` takes the key first, then sweeps the unspent allowance back to the treasury, then stops the enclave set, then records the retirement in the fleet ledger — and only then checks that all three are true: no stored session key, a zero balance, no reachable enclaves. Any one of them left standing is an error, not a warning.

## Deviations from the plan

1. **The schedule is proven by its arithmetic, not by the passage of a day.** The drill cannot advance the chain clock to make a session nearly expired: the enclaves re-validate against the **wall** clock (the T-2.7 clock-skew finding), so a chain that jumps 84,600 seconds forward issues policies the enclaves then refuse as starting in the future. I tried it; the next check failed with *enclave 1 did not return a signature share*. The drill therefore shows the scheduler with two leads: with a one-hour lead nothing is due, with the fleet's one-day lead both agents are due. The arithmetic across now, lead and expiry is covered in `tests/application/test_session_schedule.py`.
2. **The gas deposit is not swept.** "No outstanding allowance" here means the agent account's spendable balance, which under ADR-006's budget-by-funding *is* the allowance. The account's EntryPoint deposit stays with the EntryPoint: it can only pay for gas, the EntryPoint is not among the agent's allowed session targets so the agent could never have moved it, and after the teardown there is no session key at all. Withdrawing it would need an owner operation whose own prefund comes out of the balance being withdrawn.
3. **Iteration feedback is delivered, not read.** The loop hands each attempt's failures to the next generation. The stand-in proposer records them and changes its proposal by attempt number, because there is still no model (IG-5, ADR-006 §7.1). What the loop proves is the control around the model, not the model's ability to learn.

## Design decisions (please review)

1. **The monotonic rule compares a candidate with the previous attempt, not with the task specification.** T-5.6 already refuses anything beyond the owner's ceiling. This is tighter: inside that ceiling, an automatic iteration still may not grow. An agent that asks for more room after failing has to ask the owner.
2. **A renewal is strict equality except the window.** Not "no widening" — identity. A changed prompt or a changed name widens nothing, but it is a different agent, and a different agent needs a human. So `is_renewal` compares the whole definition with the window normalised away.
3. **Any change of the rolling window is a widening**, in either direction, because the window is the denominator of every cap and the T-5.4 finding was that a session crossing a window boundary doubles the worst case.
4. **A changed owner is a widening.** It grants authority to someone the previous owner did not name.
5. **Retirement verifies instead of trusting.** Each port reports its own end state and `RetireAgent` reads all three back. The drill's teardown adapter skips an uninstall that is already done, so retiring an agent whose validator was revoked by hand still ends in the same verified state.
6. **The lifecycle holds the definition in force**, so the renewal comparison and the iteration comparison use the same source of truth, and the drill can assert that a refused iteration or a refused renewal left it untouched.

| T-5.8 acceptance criterion | Where it is proven |
|---|---|
| An iteration that would widen caps, payees or the window is refused and escalated to a fresh human approval (I-9, I-13) | `test_an_iteration_that_would_widen_authority_is_refused`, `test_an_iteration_that_widens_authority_is_escalated_not_installed`, and the drill's "an iteration that would widen authority is escalated, not installed" |
| The iteration budget is bounded and enforced | `test_the_attempt_budget_is_enforced`, `test_the_cost_ceiling_is_enforced_across_attempts`, `test_a_candidate_that_keeps_failing_is_escalated_at_the_attempt_budget`, and the drill's "a failing candidate is iterated inside a bounded budget" |
| A retired agent has no session key, no outstanding allowance and no reachable enclave set | `tests/application/test_agent_retirement.py` for each of the three, and the drill's "a retired agent keeps no key, no allowance and no enclaves", which sweeps the real balance to the treasury and stops the real enclave processes |
| A rotation happens on schedule without a human for a renewal of the same authority, and never for a widened one | The drill's "a session renews on schedule without a human, a widened one never does": the scheduler reports the agent due, a renewal that doubles the cap is refused before any ceremony starts, and the renewal of the same authority runs through T-2.7 with no human and no change to the cap on chain |

- **Drill: 41 of 41** (37 before), on two consecutive runs of the final code. The four new checks report: the loop accepted on attempt 2 of 3 for 3,600 of 500,000 micros after being handed the first attempt's failures, and asked for no more authority than attempt 1; a second attempt that raised its own cap from 0.25 to 0.5 ETH was escalated, not installed, with the standing authority still the first attempt's; with a one-hour lead the scheduler reported nothing due and with the fleet's one-day lead it reported two sessions due, a renewal doubling the cap was refused and the renewal of the same authority ran unattended; and the retired agent returned 0.07 ETH of unspent allowance to the treasury, freed the same amount of the approved total, and left no key, no balance and no reachable enclaves.
- **Mutations: 45 at unit level, 45 caught** after one fix (below).
- **Two drill-level mutations**, both caught. Letting an iteration widen authority again makes the escalation check report *an iteration that widened authority was accepted*; never stopping the enclave set makes the teardown check report *agent-two still has reachable enclaves* — the verification, not the drill, is what notices.

### What the mutations taught me

One mutation survived the first pass, and it was a real gap rather than a redundant line. Removing the `widenings` guard at the top of `is_renewal` changed nothing in any test, because for most widenings the field-by-field equality that follows already says no. But `is_renewal` normalises the window away before comparing — so a session that runs **longer** than the one before it compares equal, and without the guard it would have been called a renewal. `require_renewal` would still have refused it (it checks `widenings` first), so nothing in the live path was wrong; what was wrong was that no test pinned the behaviour of `is_renewal` itself on a longer session. The fix adds that assertion, and the refusal, to `test_a_longer_session_is_a_widening_and_never_a_renewal`.

## Risks and limits

- **An unattended renewal installs a key the owner never saw.** That is what the criterion asks for, and it is a real reduction in what the T-5.4 fingerprint means: the owner approved a specific (definition, policy, key) triple, and the renewal replaces the key under the same authority. The mitigation is the provenance entry, which records the new fingerprint and names the scheduler as the approver, so the chain always says which key is in force and who installed it. The `ProvisionedAgent` record kept from the first approval is deliberately not re-signed.
- **Nothing drives the scheduler.** `due_for_renewal` answers a question; no process asks it on a timer. Wiring it to a service is T-5.9 work and needs the observability from R-NEW-14.
- **The lifecycle is in memory.** It lives for one run. A real fleet needs it stored, and recovering it from the provenance chain would need the chain to carry every state move, which it does not: it carries generation, derivation, evaluation, approval, installation, renewal and retirement, but not refusals or iterations.
- **Rejected attempts are not recorded.** Only the accepted candidate reaches the provenance chain, with the attempt count and the loop's total cost in its generation entry. An escalation leaves nothing behind but the outcome the caller holds.
- **The monotonic rule reads definitions, not behaviour.** An iteration can keep every limit and still make the agent worse. That is evaluation's job (T-5.7), and it runs on every attempt.
- **The cost ceilings are mine.** 3 attempts and 500,000 micros per loop; no project document sets either, and neither is calibrated against a real provider's prices.
- **Still local:** simulated attestation, development keys, Alto with safe mode off, no Base Sepolia, unaudited.

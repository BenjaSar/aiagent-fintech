# T-5.5 — a runtime for one payment agent

2026-11-21. Fifth task of the agent-factory program (`docs/agent-factory-program-plan.md`), and the first that **runs** an agent rather than governing one. A payment agent now looks up its payees, reads its balance and pays an approved payee end to end through the drill, exactly once per idempotency key, without ever being able to reach a key or submit an operation itself. No contract changed.

## What changed in practice

**A tool boundary with four tools and two gates** (`application/agent_tools.py`). `ToolRunner.invoke` takes a name and string arguments and returns text lines, the shape a tool protocol would carry. Every call passes two checks first: the tool must be in the catalog, and it must be one **this agent's definition was given**. A tool the catalog names but this build does not implement is refused as well. Then:

| Tool | What it does |
|---|---|
| `list_payees` | The agent's own approved payees, with their registry labels |
| `get_balance` | The agent account's balance, for a declared asset only |
| `get_payment_status` | One payment by its idempotency key |
| `pay_payee` | Resolves a payee identifier to its approved address, opens a journal entry and emits one intent |

**A payment journal that makes retries safe** (`application/payment_journal.py`). `open` returns the existing entry when the same intent arrives again, and refuses outright when one key is reused for a *different* payment. An entry settles or is refused once. The journal, not the tool's text, is the system of record, and the drill reads its totals.

**A bounded loop** (`application/agent_runtime.py`). `AgentRuntime.run` asks a `PaymentDecider` for the next action, invokes the tool, feeds the result back, and stops on `Finish` or at a step limit. The decider is a port: `ScriptedPaymentDecider` drives it deterministically today, and a model would implement the same port later.

**A sink that verifies the money moved** (`composition/runtime_local.py`). The drill's `DrillIntentSink` turns an intent into a session operation, has the quorum sign it and submits it — and then reports `settled` only if the payee's balance rose by exactly the amount. A reverted operation is recorded as refused rather than quietly as paid.

## Isolation, checked structurally

I-10 says the runtime holds no key material and cannot submit a `UserOperation`. That is now a test, not a claim. `tests/application/test_runtime_isolation.py` parses the source, walks the transitive `fintech_agent` imports of the runtime, the tool runner and the decider, and asserts that none of them can reach FROST, the signer, the enclave node or service, the key-share record, DPAPI storage, the enclave or bundler transports, the Foundry toolkit, rotation, or any composition module. A second test is the positive control: the same walk run against the drill toolbox **does** find the signer and FROST, so the walk is not vacuous. A third asserts the ports the runtime is handed expose exactly one method each — `submit`, `decide`, `run`.

## Deviation from the plan

T-5.5 in the program plan says "the stage 1 tools as MCP servers (T-3.2)". **No MCP wire protocol is implemented.** The tools sit behind an invocation boundary with the shape MCP uses — a name, string arguments, text results — so T-3.2 can serve them without changing the runtime, but nothing speaks MCP yet, and T-3.2 remains unbuilt. I chose not to half-build a protocol whose own task has not been done.

## Design decisions (please review)

1. **The decider is a port, and stage 1 fills it with a script.** ADR-006's C4 is about a system that *authors* agents; a model driving each payment is a separate concern the plan does not require for stage 1. The loop, the tools, the idempotency and the isolation are real; the brain is deterministic, and the seam where a model goes is explicit.
2. **Tools return text, the journal holds the truth.** Text results suit a model reading them later; anything that must be checked — did this payment settle, how much has settled — is read from the journal, never parsed out of a tool's prose.
3. **Payees are named by identifier all the way through.** The task, the tool arguments and the definition all speak identifiers; only the tool runner resolves one to an address, and only from the agent's own approved payees. A task naming a stranger is refused before an intent exists.
4. **The capability check is repeated at call time.** The approval already bounded the tools, but the runner checks again on every call, so a decider cannot reach a tool the owner did not grant even if the catalog holds it.
5. **The sink confirms the balance moved.** `submit_directly` succeeds even when an operation is included and then reverts, so without the balance check the journal would record a refused payment as settled.
6. **Payment agents are given `get_payment_status`.** The fixture agent originally had three tools, and a test failed because the runner correctly refused the status tool. An agent that cannot ask whether a payment settled cannot retry safely, so the tool was added to the stage-one set rather than the test weakened.

## Mapping to the acceptance criteria

| T-5.5 acceptance criterion | Where it is proven |
|---|---|
| A human-authored payment agent pays an approved payee end to end through the drill | The drill check "an agent's runtime pays an approved payee, once, and nothing else" |
| The model demonstrably cannot reach key material or submit a `UserOperation` | `test_runtime_isolation.py`, including its positive control |
| A retried payment with the same idempotency key does not pay twice | `test_running_the_same_task_again_pays_nothing_more`, `test_the_same_key_never_pays_twice`, and the drill check's second run |
| An intent naming an unapproved payee never reaches the enclaves, and would be refused there and on chain if it did | `test_a_task_naming_an_unapproved_payee_reaches_no_sink`; in the drill the session nonce is unchanged after the refused task, and T-5.2's checks already prove the enclaves and the hook refuse such a payment when one is forced past the runtime |

## Evidence

- **Python: 704 tests pass** (657 before, 47 new). `ruff`, `ruff format` and `mypy --strict` clean on source and tests. Solidity is untouched at 218.
- **Drill: 35 of 35** (34 before), on two consecutive runs of the final code. The new check runs the real runtime against the second fleet agent: it lists payees, reads the balance, pays 0.02 ETH to the approved payee, and the drill confirms the balance and the rolling window moved by exactly that; the same task again changes nothing and the journal still totals one payment; a task naming a stranger is refused and the agent's session nonce is unchanged, so nothing was built, signed or submitted.
- **Mutations: 23 at unit level, all caught** — the journal's key clash, its already-known reply, its settle-once rule and both halves of its settled total; the runner's capability, handler, already-paid, payee, asset and amount checks, its settle-or-refuse choice and its failure flag; the loop's finish, its bound and its history; the decider's payment step and both summary branches; and the intent's key, amount and address rules.
- **Two drill-level mutations**, both caught. Paying half of what the intent said is refused by the sink's balance check and the agent reports "the payment did not reach the payee"; a journal that never reports a key it already knows breaks the retry outright with "drill-invoice-0001 is already settled".

## Risks and limits

- **No MCP** (the deviation above), so nothing external can call these tools yet.
- **The decider is scripted.** Nothing here exercises a model's judgement, and a model-driven decider would bring its own failure modes — injection through tool results chief among them. The tool results are already bounded text from the agent's own registry and journal, which limits that surface, but it is untested against a model.
- **The journal is in memory.** A restart loses it, and with it the idempotency guarantee across restarts; two runtimes sharing one agent would double-pay. A durable, single-writer journal is needed before anything real.
- **The sink's balance check is not a receipt.** It infers settlement from a balance change, so a concurrent transfer to the same payee in the same block could mask a refusal. Reading the operation's own receipt would be stronger.
- **One asset, one agent, one task shape.** The runtime pays native currency to one payee per task; no batching, no tokens in the drill, no scheduling, no retry policy beyond idempotency.
- **The isolation test is structural.** It proves the runtime's modules cannot import a signer. It does not prove that a *caller* cannot pass a key-bearing object into a port at runtime; the ports' one-method shape is the only guard there.
- **Still local:** simulated attestation, development keys, Alto with safe mode off, no Base Sepolia, unaudited.

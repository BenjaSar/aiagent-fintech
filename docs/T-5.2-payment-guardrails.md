# T-5.2 — payment guardrails in the hook

2026-11-20. Second task of the agent-factory program (`docs/agent-factory-program-plan.md`), and the only safety-critical contract change in stage 1. It turns the fleet of T-5.1 into **payment** agents: an agent in a payments-only scope can send value to approved payees and nothing else. Everything is local.

## What changed in practice

**The hook gained a payment profile.** `onInstall` now takes `(address[] targets, AssetRule[] rules, address[] payees, bool paymentsOnly)`. When `paymentsOnly` is set for a scope, three new gates apply to every session execution:

| Gate | Refusal |
|---|---|
| A value payment must name an approved payee | `PayeeNotAllowed(payee)` |
| A value payment must carry no call data | `CallDataNotAllowed(target)` |
| A token call must be `transfer`, never `approve` | `ApprovalNotAllowed(token)` |
| A token `transfer` recipient must be an approved payee | `PayeeNotAllowed(recipient)` |

Payees are managed like targets and caps, by the account itself: `allowPayee`, `revokePayee`, with `isPayeeAllowed` and `isPaymentScope` as views. Nothing changes for a scope that is not payments-only, which is why the 204 Solidity tests that existed before still pass untouched.

**The enclaves refuse the same operations before signing.** `SessionPolicy` gained `allowed_payees` and `payments_only`, and `check_operation` enforces exactly the four rules above. Both fields are required, so no policy can be built that silently omits the profile. The policy document, and therefore the policy digest and the enclave wire format, carry them.

**The approval screen stops overstating.** For an ordinary policy it still says "Call any function, with any data", because that is true. For a payments-only policy it instead says "Send up to X per rolling window, with no call data attached", "Transfer up to X … it cannot approve spending, so no allowance can outlive this session", and "Pay only the N approved payees listed below". It lists the payees, and every unlabelled payee needs its own acknowledgement ("check the address digit by digit"). It no longer warns about allowlisted targets in a payment scope, because they grant nothing there, nor about native value attached to calls it cannot make. Its "keep in mind" caveat changes too: the allowance warning is replaced by the two statements that are true of a payment scope, that it cannot call a contract or create an allowance, and that approving a payee lets that address receive money.

**Rotation carries payees.** `hook_changes` now emits `allowPayee` and `revokePayee` calls after the target and cap changes, and refuses to turn a payments-only policy into another kind — that is a profile change, not a rotation.

**The fleet agents are payment agents.** Each one is installed with `paymentsOnly` true, one approved payee, and a second allowlisted address that is deliberately *not* a payee, so the drill can isolate the payee gate.

## Design decisions (please review)

1. **An explicit flag, not an inference from a non-empty payee list.** Inference fails open when the list is empty; a flag fails closed. A payments-only policy with no payees can pay nobody, which is the safe reading of an empty list, and the screen says exactly that.
2. **Payees are an additional gate, never a replacement.** A native payee must still be an allowlisted target, and a token recipient must still be under a capped asset. A mistake in the payee list can therefore only narrow authority, never widen it. The cost is that an allowlisted target that is not a payee is dead configuration in a payment scope.
3. **`approve` is forbidden outright rather than capped.** An allowance outlives the window, the session and the agent, so for a payment agent the only safe allowance is none. This closes D19 for stage 1 without an allowance inventory.
4. **Call data must be empty.** A payment is a value transfer; anything else is a contract call, which is what T-2.2's honesty note was about and what a payment agent has no business doing.
5. **Sanctions are checked first.** The order inside an execution is infrastructure, sanctions, cap and allowlist, then the payment gates, so a listed payee is reported as sanctioned rather than as an unapproved payee. Tested in both directions.
6. **The same four rules live in two places on purpose** — the enclaves and the hook. The drill proves each one independently by forcing a compromised quorum past the enclaves and watching the hook refuse.
7. **The install ABI changed.** Nothing is deployed on any chain, so there was no migration to weigh. The hook's bytecode and address change, so every account re-attests and reinstalls; the drill does that from scratch on every run.
8. **No payee registry contract was built** (see the deviation below).

## Deviation from the plan

T-5.2 in the program plan listed four items: the payee allowlist (D20), the call-shape and selector policy (D18), `approve` forbidden (D19), and a **payee registry** (D21). The first three are done. The fourth is only half done: the hook holds the allowlist that *enforces* payment destinations, but nothing records **who approved a payee and when**. That record belongs with the provenance log, so D21 stays open and moves to T-5.4. The gap register says so.

## Mapping to the acceptance criteria

| T-5.2 acceptance criterion | Where it is proven |
|---|---|
| A transfer to a non-allowlisted payee reverts although it is inside the cap | `testAPaymentScopeRefusesATokenTransferToAnUnapprovedPayee`, and the drill check "a payment agent can only pay an approved payee" |
| `approve` reverts for a payment scope | `testAPaymentScopeRefusesAnApprovalEvenToAnApprovedPayee` |
| A call with non-empty data to a payee target reverts | `testAPaymentScopeRefusesCallDataOnAnApprovedPayee`, and the drill check "a payment agent cannot attach call data to a payment" |
| An allowlisted payee that the oracle lists still reverts (sanctions first) | `testASanctionedPayeeIsRefusedBeforeThePayeeCheck`, plus the mutation that reorders the checks |
| `onUninstall` still cannot revert | `testAPaymentScopeCanBeUninstalledAndIsThenGone` |
| One mutation per new control is caught | 10 hook mutations, all caught |
| The changed hook is re-attested and an unattested build cannot install | The drill attests the hook it deploys, and the two ERC-7484 checks from T-2.4 still pass |

## Evidence

- **Solidity: 218 tests pass** (204 before, 14 new), `forge fmt --check` clean. The new tests cover the profile declaration and its views, an unapproved token recipient, an allowlisted non-payee, an approval to an approved payee, call data on a payee, a value-only payment and a token payment that both work, a sanctioned payee, one bad payment refusing a whole batch, payee changes by the account, a stranger failing to change them, infrastructure refused as a payee, a payments-only policy with no payees, uninstalling a payment scope, and an ordinary scope keeping its wider powers.
- **Python: 519 tests pass** (495 before, 24 new). `ruff`, `ruff format` and `mypy --strict` clean on source and tests.
- **Drill: 33 of 33** (31 before), on two consecutive runs of the final code. The two new checks each prove both layers: the enclaves refuse to sign, and the hook refuses the same operation when a compromised quorum forces it on chain. The payee's `pings` counter stays at its old value, which is direct evidence that no function was called.
- **Mutations: 27 in all, every one caught and reverted.** 24 at unit level — 10 in the hook (profile ignored, call data allowed, either payee check removed, approvals allowed, profile dropped at install, payee list dropped at install, infrastructure allowed as a payee, revocation that does not revoke, and the sanctions check moved after the payee check) and 11 in Python (each of the four policy rules, the payees-need-a-profile validation, the recipient offset, the rotation payee diff, the profile anchor, and the three screen changes, plus three more for the caveat choice, the payee count and the value warning). Three at drill level: the hook ignoring the payment profile and the agent installed without the profile on chain both let the forced payment through, and the drill failed with "agent-one changed state although nothing should have moved"; giving the enclaves a policy without the profile failed even earlier, at provisioning, because `SessionPolicy` refuses payees without the profile.
- **Rendering the screen found three misdescriptions**, which is what T-2.6 exists to prevent: it said "the 1 approved payees", it kept the caveat about an allowance the agent cannot create, and it warned about native value attached to calls a payment scope cannot make. All three are fixed, each with its own test and its own mutation.
- Two of my own new tests failed on first run and were wrong, not the code: a "dirty address word" built with the non-zero byte in the wrong position, and a normalization test on an all-digit address, where uppercasing changes nothing. Both are fixed; the second is a reminder that an address used to test normalization must contain letters.

## Risks and limits

- **No payee provenance** (the deviation above). Nothing records who approved a payee; T-5.4.
- **One payee list for both assets.** A payee approved for native currency is also approved for every capped token. Per-asset payee lists would be finer; not built.
- **A reinstall needs the whole list again.** Uninstalling bumps the epoch and orphans the scope, so payees must be supplied again at the next install. That is what lets `onUninstall` never revert, and the rotation diff only covers changes to a live scope.
- **`transferFrom` remains undecodable.** The hook understands only 68-byte `transfer` and `approve` calls, so a payment agent cannot pull funds at all. Fine for stage 1, a gap for anything else.
- **The hook still cannot see what a payee does with the money** (unchanged from T-2.3), and a payee is only as good as the user's check of the address.
- **Gas is not measured.** The payment path adds a profile read and a payee read per execution, and two on the token path (T-1.8, T-V1).
- **Dead configuration is possible.** An allowlisted target that is not a payee grants nothing in a payment scope and the screen does not mention it, so a policy can carry a misleading target list.
- **Unaudited** (T-V2), local only, simulated attestation, Alto with safe mode off, no Base Sepolia.

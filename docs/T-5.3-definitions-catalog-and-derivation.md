# T-5.3 — agent definitions, the tool catalog and policy derivation

2026-11-20. Third task of the agent-factory program (`docs/agent-factory-program-plan.md`). It gives the project its first artifact that *is* an agent, the catalog that bounds what an agent may be given, the registry that bounds who it may pay, and the mechanical step from a definition to an on-chain authority. No model is involved and no contract changed.

## What changed in practice

**An agent definition is now a first-class artifact** (`domain/agent_definition.py`): schema version, agent type, name, purpose, model and sampling parameters, system prompt, declared tools, payees by registry identifier, per-asset caps, window, validity, funded budget, risk tier, owner and provenance identifier. Every field is validated on construction. `agent_definition_document.py` gives it a canonical document, a `document_digest` and a `definition_digest`, following the pattern already used for the Agent Card body and the session policy.

**A tool catalog bounds capabilities** (`domain/tool_catalog.py`). Stage 1 holds four tools: `list_payees`, `get_balance` and `get_payment_status` read, and `pay_payee` carries authority. A definition may reference catalog entries only, each once.

**A payee registry bounds destinations** (`application/payee_registry.py`). Each entry carries an identifier, an address, a label, the approver and the approval time. A definition names payees by **identifier**, never by address.

**Derivation turns a definition into a policy** (`application/policy_derivation.py`). `derive_session_policy` takes the definition, the deployment parameters, the catalog and the registry, and produces the `SessionPolicy` the enclaves and the hook already understand: the payee addresses as both the allowlist and the payee list, the declared caps as rules, `payments_only` set, the validity window with the clock-skew margin, and the validator, hook, paymasters, gas limit and window taken from the deployment.

**The drill now derives everything.** Each fleet agent gets a definition, its policy is derived from it, and **both** the sealed enclave policy and the on-chain hook install data are built from that one derived policy, so the two layers cannot drift. The drill also checks that the window installed in the validator is the window the policy derived.

## Design decisions (please review)

1. **Payees are named by registry identifier, not by address.** This is the I-11 argument in concrete form: a generator that could write raw addresses could name an attacker's address, and only the human approval would stand between that and a payment. An invented identifier simply does not resolve. The labels it carries also let the approval screen name a payee instead of showing bare hex.
2. **The temperature is an integer in hundredths.** The definition is canonicalized for its digest, and floating point is the classic canonicalization hazard — the same reason the Agent Card parser refuses floats (T-2.5 decision 2). `temperature_hundredths` keeps the digest exact.
3. **Derivation decides nothing the deployment owns.** Validator, hook, paymasters, maximum gas cost and the window come from `DeploymentParameters`. A definition cannot point its agent at another hook, raise its own gas allowance or choose its own validator.
4. **A window that disagrees with the hook is refused**, with the hook's own number in the message, because a mismatch would make the enclave ledger and the on-chain window count differently.
5. **Derivation produces no dead configuration.** The allowlist is exactly the payee addresses; a capped token is never a target, because the hook refuses a target that has a cap. A payee that is also a declared asset is refused rather than silently dropped. One consequence: the drill can no longer isolate the payee gate with an allowlisted non-payee, so that isolation now lives only in the Forge test `testAPaymentScopeRefusesAValueTransferToAnAllowlistedNonPayee`.
6. **The clock-skew margin is a deployment parameter.** T-2.7 found the chain-clock against wall-clock problem the hard way; it is now explicit, derived into every policy, and tested, including that the start never goes below zero.
7. **The registry closes D21 here rather than in T-5.4.** My T-5.2 report moved the payee registry to T-5.4; building derivation needed it now, and it records the approver and the approval time, which is what D21 asked for. The append-only provenance log for a whole generation is still T-5.4.

## Mapping to the acceptance criteria

| T-5.3 acceptance criterion | Where it is proven |
|---|---|
| A definition naming an uncatalogued tool is refused | `test_an_uncatalogued_tool_is_refused` |
| A definition whose window disagrees with the hook is refused | `test_a_window_the_hook_does_not_count_is_refused` |
| A payee not in the registry is refused | `test_a_payee_outside_the_registry_is_refused` |
| The derived policy for a known definition is byte-stable | `test_the_same_definition_derives_the_same_policy_every_time`, comparing both the policy and its digest |
| Every derived policy passes the T-2.6 screen or is refused with its reason | `test_the_derived_policy_passes_the_approval_screen_with_registry_labels` and `test_a_derived_policy_the_screen_refuses_is_refused_with_its_reason` |

## Evidence

- **Python: 623 tests pass** (519 before, 104 new). `ruff`, `ruff format` and `mypy --strict` clean on source and tests. Solidity is untouched at 218.
- **Drill: 33 of 33 on two consecutive runs** of the final code, with every fleet policy derived from a definition and the installed on-chain window checked against it.
- **Mutations: 27 at unit level, all caught**, across the catalog (duplicate and empty tool lists, the payment-authority test, the summary text rule), the definition (schema version, duplicate tools, payee identifier shape, the budget naming an asset the agent cannot move, risk tier, plain text, the name pattern), the document (the amounts-as-strings rule and sorted keys), the registry (duplicate identifier and address, the label rule, the approval time, duplicate resolution) and derivation (the window check, the paying-tool check, the needs-a-payee check, the role-clash check, both halves of the clock-skew margin, the allowlist, the payments-only flag and the caps).
- **Two drill-level mutations, both caught.** Installing the validator with a window the policy did not derive fails the provisioning check with "agent-one holds the window (0, ...), not the derived (...)"; dropping the clock-skew margin in derivation makes the enclaves refuse to sign at the first payment ("enclave 1 did not return a signature share"), which is the T-2.7 failure mode now caught automatically.
- **One unit mutation survived at first**, and it mattered: removing `sort_keys` from the digest. My order-independence test was vacuous — it round-tripped the reordered document back into a definition, and `definition_to_document` always emits the same key order, so nothing was ever reordered at serialization time. Fixed by exposing `document_digest` and digesting the reordered document directly; the mutation is now caught.

## Risks and limits

- **Nothing generates definitions yet.** They are written by hand; the drill writes two. The generator is T-5.6, and until then the catalog and the registry bound a human author rather than a model.
- **The registry and the catalog are in memory and unauthenticated.** Anyone who can call `approve` can add a payee. Who may approve, and how that approval is recorded durably, is T-5.4's question (I-9).
- **No approval binding yet.** A derived policy is not yet tied to a definition digest and a session key in one user approval; that is T-5.4 and the extended T-2.7 fingerprint. Until then, deriving a policy proves nothing about who agreed to it.
- **The model fields are recorded and never used.** Nothing in the repository calls a model.
- **The system prompt is bounded and plain, but its content is unchecked.** I-11 holds because the prompt grants nothing, not because anything understands it.
- **Stage 1 only:** one agent type, one payment profile, no `transferFrom`, no x402, no per-asset payee lists.
- **Local, unaudited, simulated attestation,** as before.

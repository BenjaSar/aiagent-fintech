# T-5.1 — fleet authority plane

2026-11-20. First task of the agent-factory program (`docs/agent-factory-program-plan.md`). It makes the authority plane hold **more than one agent authority at a time**, which nothing in the repository could do before: the validator keeps one session key per account, the hook scopes every cap and window by account, and an enclave set accepts one policy. No contract changed. Everything is local.

## What changed in practice

**One account per agent.** Each agent gets its own smart account from the existing `FintechAccountFactory`, at a deterministic salt derived from its identifier (`domain/fleet_identity.py`: SHA-256 over a domain tag and the identifier). The account is created by the same owner-signed operation that installs its session validator, and the policy hook is installed next. Validator and hook are the already attested deployments, so the ERC-7484 gate applies unchanged.

**A treasury that holds the money and no authority.** A separate account at the reserved `treasury` salt holds the pooled funds. It has no validator and no hook, so only the user's owner key can move anything out of it. Each agent is funded by an owner-signed transfer from the treasury to the agent account.

**Budget by funding (ADR-006 D-4).** Gas for every agent comes from its EntryPoint deposit, and the hook forbids the EntryPoint as a target, so a session operation can never turn gas into a payment. The agent account's native balance is therefore exactly its remaining allowance, and the account balance is the bound on total authority (I-13). No new on-chain budget feature exists.

**One enclave set per agent.** Each agent gets three enclave processes of its own, runs its own distributed key generation, and receives its own sealed session policy. Sets live under `.local\enclave-sets`, which is also where rotation now puts its sets (renamed from `.local\rotations`, since both features create sets).

**A ledger for the approved total** (`application/fleet_ledger.py`). It refuses a duplicate agent, a shared account, a malformed address or identifier, and any funding that would take the fleet past the total the user approved.

## Design decisions (please review)

1. **Account per agent rather than multi-tenant contracts.** ADR-006 §4 records the reasoning: it leaves the validator and the hook untouched, keeps their test and mutation evidence intact, and gives per-agent accounting and isolation for free.
2. **The ledger counts funding, not approvals.** Retiring an agent does **not** free budget, because the retired account still holds its funds. Only `record_sweep` reduces the counted total. There is no sweep procedure in the repository, so the ledger is the only place that currently keeps this honest.
3. **Deposits are deliberately outside the budget.** An EntryPoint deposit is gas-only. Counting it as budget would weaken the balance-equals-allowance property that the whole bound rests on.
4. **The drill switches the account under test** through one `acting_as` context manager on the toolbox, which saves the account, enclave set and policy and restores them afterwards, because the toolbox was written for a single account. The same mechanism rotation already used for enclave sets now covers the account and the policy too.
5. **Agents do not get a recovery module.** Their owner is the user's own key, so recovering that key covers every agent account, but the guardian path (T-1.1, step 9) exists only on the account where it was installed. A per-agent guardian set was not added, and the implication is in the risks below.

## Mapping to the plan's acceptance criteria

| T-5.1 acceptance criterion | Drill check |
|---|---|
| Two agent accounts exist with separate keys, caps and windows | "a treasury and two agent accounts hold separate, funded authorities" |
| Neither can spend the other's budget | "one agent cannot use another agent's key, policy or window" |
| An agent cannot spend more than its account holds, even inside its cap | "an agent cannot spend more than it was funded, even inside its cap" |
| Revoking agent A leaves agent B working | "revoking one agent leaves the other paying and the treasury intact" |
| The treasury itself holds no session authority | checked in the first and the last of those four |

## Evidence

- **Drill: 31 of 31 checks pass** (27 before), on two consecutive runs of the final code. The four new checks prove, in order: distinct accounts, group keys and policies, each agent holding exactly what it was funded with, the treasury holding no session key, and the ledger refusing a third agent that would exceed the approved total; the second agent's enclaves refusing to sign for the first account, a signature from their quorum rejected on chain with AA24, and one agent's spending leaving the other's rolling window untouched; a payment of 0.5 ETH that the enclaves **did** sign because it is inside the 1 ETH cap, refused on chain because the account held 0.2 ETH, with nothing moved and the window uncharged, followed by a payment within the balance that executed; and an agent whose validator is uninstalled failing with AA24 on a payment its own quorum had signed beforehand, while the other agent pays on and the treasury is untouched.
- **36 new Python tests** (495 in total). `ruff`, `ruff format` and `mypy --strict` are clean on source and tests. The 204 Solidity tests are unaffected, since no contract changed.
- **Mutation checks, 15 in all, each caught and then reverted:** removing or loosening the approved-total bound; letting a retired agent's funding be reused without a sweep; sweeping an agent that was never retired; accepting a duplicate account or identifier; skipping identifier validation; accepting an unfunded member; allowing `treasury` as an agent name; loosening the identifier pattern; making the salt independent of the identifier. At drill level: over-funding every agent (caught by the funding check), giving every agent the same account (caught at provisioning, AA10 sender already constructed), and removing the enclave check that an operation belongs to its policy's account (caught by the cross-agent check).
- A **vacuity guard** in the over-balance check refuses to pass if the payment is not simultaneously above the balance and inside the cap, so the check cannot silently become trivial.

## Risks and limits

- **These are not yet payment agents.** The hook still cannot restrict a payee or a call shape: an allowlisted target can be called with any data, and a capped token accepts `transfer` and `approve` alike. T-5.1 proves isolation and the funding bound, not payment safety. That is T-5.2, and it is the only safety-critical contract change in stage 1.
- **One enclave set per agent does not scale.** Three processes and one DKG per agent bounds a local fleet to single digits (D23c, D9). Multi-tenant enclaves are T-5.9.
- **No scheduler and no sweep.** Nothing rotates an agent before expiry and nothing returns a retired agent's funds to the treasury, so liquidity fragments and the ledger's `record_sweep` has no counterpart on chain (T-5.8).
- **No guardian path per agent account** (decision 5). If the user's owner key is lost, recovery must be exercised on each agent account separately, and the module is not installed there.
- **The fleet shares one owner key.** That is the intended design — the user owns every agent account — but it means the owner key is the single point of failure for the whole fleet, as it already was for one account (I-1).
- **The approved total lives in memory.** `FleetLedger` is not persisted, so the bound is enforced only within one process. A durable record belongs with the provenance log (T-5.4).
- **Local only.** Simulated attestation, development keys, Alto with safe mode off, no Base Sepolia, no audit.

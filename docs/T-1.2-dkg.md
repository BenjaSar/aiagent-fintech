# T-1.2 — distributed key generation (step 5b)

2026-11-16. Pure domain code in `src/fintech_agent/domain/frost/dkg.py`; no transport, storage or enclave process yet.

## Correction to the project's assumption

The project notes (B-6) assumed RFC 9591 defines a DKG. It does not: Appendix C specifies only trusted-dealer key generation, and the security section says shares come from a dealer "or through a distributed key generation protocol" without defining one. The DKG here follows the FROST paper's Figure 1 (a Pedersen DKG with a Schnorr proof of knowledge per participant), as described and implemented by the Zcash Foundation. The paper itself could not be fetched (bot challenge on eprint.iacr.org, not bypassed), so `specs/` holds the ZF FROST Book page and the frost-core 3.0.0 source instead.

## Protocol as implemented

1. **Part 1** (`dkg_part1`): each participant draws `t` coefficients, publishes the commitment `g^coefficient` for each, and a Schnorr proof of knowledge of the constant term.
2. **Part 2** (`dkg_part2`): verifies every other participant's package (right sender, `t` non-identity commitments, valid proof), then produces one share `f_i(l)` per other participant and keeps `f_i(i)`.
3. **Part 3** (`dkg_part3`): checks each received share against its sender's commitment, sums to the secret share, and derives the group public key and every participant's verifying share from the combined commitments. A failure names the culprit.

No party ever holds the full key; the tests recompute the summed secret only to check the result.

## Decisions to review

- **DKG challenge hash is ours.** The sources leave it to each ciphersuite and do not define it for secp256k1. It is `hash_to_scalar` over `identifier ‖ commitment₀ ‖ R` with domain tag `FROST-secp256k1-SHA256-v1dkg`, next to the RFC's `rho`, `chal` and `nonce` tags. This is not interoperable with other FROST implementations, which is acceptable because only our own enclaves run it.
- **No context string**, following the ZF variant, which dropped it after further analysis.
- **Identifiers are 1 to n**, and the threshold is at least 2.

## Channel requirements, enforced outside this module

- Round 1 packages need a real broadcast channel: if participants see different packages the key generation is insecure. `transcript_digest` hashes all round 1 packages in a fixed order so participants can compare digests (an echo check); wiring that comparison is part of the coordinator in step 6.
- Round 2 packages carry secret shares and must travel over authenticated, confidential channels. The domain objects hold them in plaintext, so the enclave adapters must encrypt.

## Verification

- 22 DKG tests, all passing: 2-of-3 and 3-of-5 runs agree on one group key; verifying shares match each secret share; any threshold subset reconstructs the summed secret; DKG shares sign through the RFC 9591 aggregation and verify under the group key for several quorums, and a signature altered below that does not; forged and borrowed proofs, wrong-length commitments, missing or extra packages, tampered and misaddressed shares are rejected with the culprit named; randomness and parameter validation.
- `ruff`, `mypy --strict` and the full Python suite (99 tests) pass.
- A mutation check on the proof verification was started but the test run was blocked by the tool's permission classifier, so it was **not completed**. The edit was reverted and the file confirmed free of the change.

# T-1.8 — Solidity Schnorr verifier: gas, latency and go/no-go

Measured 2026-11-16 with Foundry 1.9.0 (solc 0.8.28, `evm_version` cancun) in its local EVM. Nothing was deployed to Base Sepolia.

## What was built

`contracts/FrostSecp256k1.sol` verifies an RFC 9591 FROST(secp256k1, SHA-256) signature on the EVM. It accepts the 33-byte compressed group commitment, the response scalar, the 33-byte compressed group public key and the message, and returns a boolean.

1. The challenge is computed exactly as in RFC 9591: H2 over `R || PK || message`, built from `expand_message_xmd` with the SHA-256 precompile.
2. The check `z·G = R + c·PK` is evaluated with the `ecrecover` precompile. Setting `r = PK.x`, `s = -c·PK.x` and `hash = -z·PK.x` (all mod n) makes `ecrecover` return the address of `z·G - c·PK`. That address is compared with the address of the decompressed commitment `R`.
3. The commitment's y coordinate comes from the modexp precompile, with an on-curve check.

## Gas (valid signatures, measured through an external harness call)

| Case | Gas |
|---|---|
| Valid signature, 7 calls (RFC vector and 6 generated vectors) | min 13,091 · median 13,129 · mean 13,132 · max 13,174 |
| Early rejection, malformed input | from about 1,900 |

The figures include the external call and ABI decoding of the two structs in the test harness, and warm precompile access. They exclude the validator's other work (policy checks, nonce handling) and calldata cost. The plan sets no gas budget; R-MET-3 is stated in milliseconds.

## Latency

**NOT RUN.** The 350–450 ms R-MET-3 budget covers the whole blockchain-verification phase (v2 §6), and gas does not convert to wall-clock time. Measuring it needs a deployed validator, a funded account and a bundler on Base Sepolia, which is T-V1. For context only: the 15-test Solidity suite ran in 3.3 ms in the local EVM, so the signature check itself is unlikely to be the dominant term.

## Go / no-go on the §6.4 contingency

On gas evidence the contingency is **not triggered**: Schnorr verification costs about 13,000 gas, so FROST per RFC 9591 can stand without switching to threshold ECDSA, and R-ARCH-2 is unchanged. This is conditional on T-V1 measuring latency on the deployed stack. A switch would still need your sign-off as a requirement change.

## Verification

- 15 Solidity tests pass: the RFC 9591 E.5 vector, 6 vectors covering all four parity combinations of public key and commitment, and 12 negative test functions (some with several sub-cases) (tampered response, wrong message, wrong key, flipped parities, altered commitment coordinates, zero, at-order and above-order responses, malformed prefixes and lengths, coordinates at or above the field prime, key coordinate at the group order).
- The 6 generated vectors come from the T-1.6 Python reference, so they check agreement between the two implementations, not independence from the reference. Only the RFC vector is independent.

## Security notes for the T-V2 audit

- The commitment is compared by 160-bit address, not by full point. A forgery needs an address match against a fixed target with a free response value, which is a preimage-style search on 160 bits. This is the standard `ecrecover` Schnorr trade-off and needs auditor sign-off.
- The public key is not checked to be on the curve inside `verify`; `ecrecover` returns the zero address when no point exists, which is treated as failure. T-1.3 must validate the key when the session validator is installed.
- Keys whose x coordinate is zero or at or above the group order are rejected.
- The library is unaudited. `forge build` reports five lint warnings (`ecrecover` malleability, two unsafe typecasts, two `encodePacked` collision notices). Each was reviewed and is intentional: `s` is deliberately arbitrary in this construction, the typecasts truncate on purpose or cannot overflow, and the packed inputs are either fixed-length checked or follow the RFC layout. They are not suppressed.

# T-1.1 — account and factory (step 3 spike)

2026-11-16. Local only; nothing is deployed to Base Sepolia.

## Decision: OpenZeppelin account (D3)

Chosen over a hand-written minimal account. Basis: the spike compiled and passed an end-to-end flow through the etched canonical EntryPoint v0.8 (53 Solidity tests in total).

- Dependency: OpenZeppelin Contracts v5.6.1, commit `5fd1781b1454fd1ef8e722282f86f9293cacf256`, cloned by `scripts/fetch-dependencies.ps1` into `lib/` (untracked) and checked against that commit. Its account contracts carry a `draft-` prefix and no audit statement was found, so they need T-V2 like our own code.
- `contracts/FintechModularAccount.sol`: `AccountERC7579` plus `SignerECDSA` and `Initializable`. `entryPoint()` is overridden to the v0.8 address (OpenZeppelin defaults to v0.9). The owner is a native ECDSA signer, so the owner path works with no module installed and cannot be locked out by removing validators.
- `contracts/FintechAccountFactory.sol`: deterministic clones. `createAccount` accepts calls only from the EntryPoint's `senderCreator`, as ERC-4337 requires; the address depends on owner and salt and on the implementation address. Since T-2.4 the factory takes the ERC-7484 registry and a default attester as constructor arguments.

## How operations are routed

- Nonce key zero (no module address): owner ECDSA signature over `userOpHash`.
- Nonce whose first 20 bytes are the validator address: the account calls `FrostSessionValidator.validateUserOp`. Nonce layout: `<validator 20 bytes> | <key 4 bytes> | <sequence 8 bytes>`.
- `uninstallModule` ignores a failing `onUninstall`, so a module cannot block its own removal (supports I-2).

## Tested through the EntryPoint (11 account tests)

Account creation by `initCode`; owner-signed install of the FROST validator; owner revokes the session key with a self-submitted `handleOps` and no other infrastructure (the I-2 drill, locally); a 2-of-3 quorum signature produced by the Python reference executes a call through the account; the same signature is rejected after the TTL (`AA22`), on replay (`AA25`) and over a different operation (`AA24`); a stranger's owner signature and a malformed session signature are rejected (`AA24`); the factory refuses direct calls.

The positive session test uses a signature fixed in the test file. The operation hash depends on the test contract's deployment order, not on contract code. If that order changes, print the new hash and regenerate with `python scripts/sign_session_hash.py <hash>`.

## Risks recorded, not closed

1. **(Closed locally by T-2.2, see `docs/T-2.2-policy-hook.md`.) A session-signed operation can call the account's own `installModule` and `uninstallModule`.** The validator accepts any `callData` the quorum signs, and those functions allow the EntryPoint as caller. The T-2.2 policy hook forbids self-calls from session operations and the T-2.4 ERC-7484 install gate refuses unattested modules, so a compromised quorum can no longer install a new validator on the local pipeline (`docs/T-2.4-module-registry-and-install-gate.md`). Do not treat this account as safe beyond local development.
2. The account's ERC-1271 path forwards only to installed modules, so the owner's ECDSA key cannot sign ERC-1271 messages. Acceptable for now.
3. No paymaster or social-recovery module yet (R-NEW-2, R-NEW-1); both remain in T-1.1's scope.

## Remaining for T-1.1

Paymaster, social recovery, a local deployment script, and the policy hook and install gate from Phase 2.

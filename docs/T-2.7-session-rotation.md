# T-2.7 — session rotation ceremony

2026-11-17. Scope is R-NEW-5: when a session ends, a fresh DKG, a reviewed policy and a new user grant replace it, automated end to end (ADR-002). Everything runs on the local pipeline (anvil, Alto, three local enclave processes). Nothing was run on Base Sepolia, and no real user interface exists.

## What changed in practice

`RotateSession` (`application/session_rotation.py`) runs the ceremony against small ports. In order:

1. **Plan and pre-check.** Work out the hook changes between the old and new policy (`domain/policy_transition.py`) and run `describe_policy` (T-2.6). An impossible transition, or a policy the screen refuses (unlimited cap, token allowed without a cap, too long), stops here with **no key generated**.
2. **DKG.** A new set of enclaves provisions identities and runs the distributed key generation (T-1.2). No process holds the full key.
3. **Review and approval.** The user sees the policy screen plus a **key fingerprint** (the first 128 bits of SHA-256 over the policy digest and the new group public key). The approval must carry that exact fingerprint, the exact policy digest and every warning. A decline, or an approval for a different key, discards the new set.
4. **Policy issuance.** The approved policy is issued once to the new enclaves (T-2.1). The enclaves never hold a policy the user did not approve. A refusal discards the new set.
5. **Grant.** One owner-signed batch executes through the account: uninstall the old validator, apply the hook changes (revoke and allow targets, set caps), install the validator with the new group key and window. It is atomic: either the whole swap happens or none of it.
6. **Verify.** The validator must hold exactly the approved key and window, otherwise the rotation fails and **nothing is retired**.
7. **Retire.** The old enclaves are stopped. A failure to stop them is reported (`previous_retired = False`), not hidden.

A grant that errors but did install the approved key (for example a timeout after inclusion) is treated as done. A grant whose outcome cannot be read is reported as unknown and nothing is discarded or retired.

## Design decisions (please review)

These were not fixed by the plan, which gives only "automated end to end: DKG → policy presentation → user grant → validator reconfiguration".

1. **Rotation is a new enclave set, not a change inside the old one.** The enclaves accept a policy once (T-2.1), so a new key and policy need new enclaves. The old set keeps working until the grant is verified, and stops afterwards.
2. **The hook is not reinstalled.** Uninstalling the hook inside an operation it guards is risky, and reinstalling would reset the rolling-window accounting. The hook keeps its state; its caps and allowlist are changed through its own owner-only functions in the same batch. This is why a rotation cannot change the window length (fixed by the hook) or the account, validator, hook or chain (`TransitionError`). The drill checks that the hook's recorded spending is unchanged by a rotation.
3. **The key is part of what the user approves.** A policy digest alone would not stop a coordinator from installing a different key. The fingerprint binds both, and the check after the grant compares the on-chain key and window with the approved ones.
4. **Removals come before additions in the batch,** so an asset can change role (target to capped token or back) without the hook refusing the intermediate state.
5. **The user is simulated in the drill.** `DrillUser` renders the screen, acknowledges every warning and returns the fingerprint. A real approval surface (T-2.6 UI) is not built. The owner key signing the batch is a local test key.

## Rotation runbook (local)

1. Draft the next policy from the current one (same account, validator, hook, chain and window; new `valid_after` and `valid_until`; changed caps or targets only if intended). Start `valid_after` slightly before chain time: enclaves check their own wall clock, and in the drill the chain clock ran ahead of it (a margin of 300 s).
2. Run `RotateSession` with a key ceremony, policy issuer, approver, grantor and previous-session adapters. The local adapters are in `composition/rotation_local.py` and `composition/rotation_drill.py`.
3. On `RotationDeclinedError` or `RotationFailedError`, read its stage (`approval`, `grant`, `verify`). Before the grant, the chain is unchanged and the new enclaves have been stopped. After a `verify` failure, both sets remain; investigate before stopping either.
4. Rotate before the old session ends: the old key stays valid until the batch executes, and the new window can start earlier than the old end.
5. To stop leftover rotation enclaves, run `scripts\stop-local-enclaves.ps1`, which also stops sets under `.local\rotations`.

## Evidence

- 31 new Python tests (459 passing in total): the ceremony order and what each port receives; decline, wrong fingerprint, missing warnings, an unapprovable policy and an impossible transition (nothing generated); an enclave refusing the policy; a failed grant with and without the key installed; an unreadable outcome; verification failures; retirement failure; and the hook-change diff including ordering and every forbidden move. `ruff`, `ruff format` and `mypy --strict` are clean on source and tests.
- 27 of 27 drill checks passed on three consecutive runs. The three new checks: a declined rotation leaves the validator key unchanged, stops the new enclaves and keeps the old quorum signing; a real rotation (second enclave set, DKG, review, approval, issuance, one batch) installs the new key and window, raises the hook cap from 1 to 2 ETH, leaves the recorded window spending unchanged and stops the old enclaves; an operation signed by the old quorum before rotation is rejected with AA24 afterwards and an operation from the new quorum executes. The steps after rotation (sponsorship, halt, revocation, recovery) run against the new set.
- Mutation checks: About 25 unit-level mutations (3 survived at first and led to new tests) and 3 drill-level mutations (skipping the hook changes, skipping retirement, installing the old key) were each caught and reverted. The drill failed at the rotation step with the expected reason in each case.

## Risks and limits

- **Local only.** The enclaves are development processes with simulated attestation, DPAPI sealing and a loopback token. The owner key is a test key. A real rotation needs the user's key on a device the user controls, and the approval screen on that device.
- **No real user step.** The review is a scripted stand-in. Whether a person understands the fingerprint and the screen is untested, and showing a fingerprint does not help unless the user can compare it with something trustworthy.
- **The ceremony is not durable.** If the process running it dies between the grant and retirement, the old enclaves keep running with a key the validator no longer accepts. They cannot sign usable operations, but they should be stopped. There is no persisted ceremony state to resume from.
- **Enclave spend ledgers do not carry over.** The new enclaves start with an empty ledger, while the hook's on-chain window keeps its history. The hook stays the authority, so the new enclaves may sign operations the hook then refuses, but not the other way round.
- **Clock skew matters.** Enclaves use wall-clock time and the chain uses block time. Without a margin on `valid_after` the new enclaves refused to sign in the drill ("outside its time window").
- **Rotation cannot change the window length, the account, the validator or the hook.** Changing those needs a different procedure (hook reinstall, owner-signed), which is not built.
- **No scheduling.** Nothing triggers a rotation before expiry. If a session expires first, the same ceremony runs without a previous policy to replace (the unit tests cover the first-session path; the drill does not).
- **Ports do not authenticate the approver.** The ceremony trusts whatever its approver port returns. In production that port must return only a user-authenticated decision.
- **Remote attestation and a real bundler's validation rules** were not exercised (unchanged from earlier tasks).

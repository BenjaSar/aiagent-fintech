# T-2.5 — ReBAC engine and Agent Card defences

2026-11-17. Scope is R-P2-4: relationship-based access control for delegated sub-agents, and defences against Agent Card poisoning and typosquatting (research PDF §4, "Defensa Multi-Agente contra el Envenenamiento de Contexto"). Everything is off-chain Python and in memory. It is not part of the on-chain drill, and no network, wallet or contract is involved.

## What changed in practice

Three pieces, each small and separately testable:

1. **A strict Agent Card parser** (`domain/agent_card.py`). A card is accepted only if it has exactly the expected fields, no repeated fields, no floating-point numbers, no control, invisible or bidirectional characters in any text, an ASCII-only name, an https origin that is plain DNS, and endpoints that all sit on the card's own origin. It produces a canonical signed body (card without its `signature` block, sorted keys, compact) and a SHA-256 digest of it.
2. **A sub-agent registry** (`application/agent_directory.py`). The user registers a counterpart out of band with its Ed25519 public key and its card. From then on:
   - A card is trusted only if its identifier is registered, it is served from the registered origin, its signature verifies against the **pinned** key (never a key the card itself points to), and its digest equals the pinned digest.
   - A correctly signed card that differs from the pinned one (a changed description, capability or version) **quarantines** the agent. A quarantined agent is refused everywhere until the owner approves the new card (`approve_change`). This is the defence against a poisoned or "rug-pulled" description.
   - An unregistered identifier or origin that looks like a registered one (homoglyph digits, `rn`/`m`, dropped hyphen, edit distance of 2 or less, punycode refused outright) is reported as an imitation. Registration itself refuses a name or origin too close to an existing one.
3. **A task-scoped relationship graph** (`domain/relationship_graph.py`) with a controller (`application/agent_access.py`). Permissions are tuples, not tokens: a task is assigned to one agent and holds explicit `(action, resource)` grants; resources can be members of collections, and a grant on a collection covers its members (depth at most 4). A sub-task can only receive a subset of its parent's grants, cannot outlive its parent, and the chain is limited to 4 tasks. A check passes only if **every task in the chain** still allows the access, is unexpired and unrevoked, and the asking agent is the one the task is assigned to. Revoking a parent cuts off all sub-tasks. Everything else is denied. The controller also denies any agent that is not an active registered agent, so a quarantined agent loses every grant at once.

## Design decisions (please review)

These were not fixed by the plan, which gives only "ReBAC engine; Agent Card poisoning and typosquatting defences".

1. **The signature scheme is mine.** The roadmap's card names `"type": "Signature2026"` with a placeholder proof and no algorithm; no project document defines it. I defined it as Ed25519 over the canonical body described above, with the proof as 128 lowercase hex characters. This is a simplified canonical JSON, not RFC 8785 and not the JWS form of the A2A specification, and I did not check the A2A specification's signed-card format. **T-3.1 must confirm or replace this** before a card is served or a real counterpart is verified.
2. **Floats are refused in cards.** The roadmap's example has `"maxSpendLimitUSDPer24h": 1000.00`. Canonicalising floats is a known source of signature disagreements, so the parser accepts an integer or a decimal string. The roadmap's example card would be refused as written.
3. **Card contents are never used for authorisation.** A counterpart's declared capabilities, spend limit or description do not grant anything. Authority comes only from the user's registry entry and the user's task grants.
4. **Pinned key, out of band.** The key comes with the registration, not from the card or its `publicKey` endpoint. A card that points to its own key proves nothing.
5. **A bad signature does not quarantine; a good signature on a changed card does.** Anyone can send garbage, so quarantining on bad signatures would let a stranger switch off a legitimate agent. Only the key holder can produce a validly signed change.
6. **Actions are a closed set: `read` and `invoke`.** There is no spend, sign or transfer action, so a relationship grant cannot move funds. Money moves only through the session policy and hook (I-3, I-6).
7. **Lookalike detection is a heuristic.** It uses a folding of confusable characters plus an edit distance of at most 2. It will flag some legitimate similar names, which only matters at registration or for unregistered counterparts. Both outcomes are refusals.
8. **Text defences are structural, not semantic.** The parser limits length, character classes and structure. It cannot recognise a prompt-injection sentence written in ordinary words. The protection against that is the pinned digest (any change needs the owner) and rule 3 (the description is never an instruction and never grants anything). Anything that later shows a description to a model must still treat it as untrusted data.

## Schema

Relationship tuples, in Zanzibar-like notation, are held as these structures:

```
task:<id>#agent@<agent identifier>
task:<id>#grant@<action>:<resource>
task:<id>#parent@task:<id>
resource#member_of@collection
```

- Task identifier: `[a-z0-9][a-z0-9._-]{0,63}`. Resource identifier: `kind:name`, for example `dataset:prices`. No wildcards.
- Agent card fields (all required, none extra): `name`, `description`, `url`, `version`, `identity{did, erc8004Registry, agentTokenId}`, `capabilities[{name, version, description}]`, `endpoints{rpc, events, publicKey}`, `authPolicy{type="ReBAC", allowedSchemes, maxSpendLimitUSDPer24h, supportedCurrencies}`, `signature{type="Signature2026", created, creator, signatureProof}`.

## Evidence

- 102 new tests (Python total 383 passing). `ruff`, `ruff format` and `mypy --strict` are clean on source and tests.
- Mutation checks (about 40) each made at least one test fail, and were then reverted. Three survived at first and led to new tests: the confusable-character folding beyond edit distance, exact-name duplicates at registration, and confusable names at registration.
- The negative cases covered: tampered body, wrong key, key of the wrong length, forged card for a registered identity (no quarantine), signed change (quarantine, then owner approval), same identifier from another origin, lookalike origin and name, punycode, non-ASCII and IP hosts, off-origin endpoints, invisible characters, repeated and extra fields, floats, expired, revoked, wrong-agent and out-of-scope tasks, sub-task widening, outliving a parent, chain depth, shrinking collections, membership cycles.

## Risks and limits

- **The registry and graph live in memory.** Nothing persists, nothing is signed by the user, and there is no authentication of who calls `register`, `approve_change` or the graph's grant operations. The owner path (who may approve) is not designed here; it needs the user's authenticated decision (T-2.6 is the approval surface).
- **Not wired to any caller yet.** Nothing in the signing, MCP or A2A path calls these checks. T-3.1, T-3.2 and T-3.3 must do so, and a missing call would silently bypass them.
- **Signature scheme unconfirmed against A2A** (decision 1), and the ERC-8004 identity is only syntax-checked: the registry address and token are not resolved on chain (T-1.4).
- **No replay or freshness check.** A validly signed old card is accepted if its digest equals the pinned one. The `created` field is checked for format only. Revocation of a counterpart's key is a manual `remove`.
- **Heuristic lookalikes.** Homoglyphs outside the folded set and longer-distance squats are not detected, and the registry only protects names the user has registered. An attacker the user registers by mistake is trusted.
- **Context poisoning is contained, not detected.** A poisoned sub-agent is stopped by scope, expiry and revocation, but the engine does not look at what the agent says.
- **Concurrency is not handled.** The structures are not thread-safe.

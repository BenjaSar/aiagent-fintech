# T-2.1 — enclave-side re-validation of session operations

2026-11-17. Scope is R-NEW-4 and invariant I-8 for the second half of T-2.1: each enclave validates the user operation against the session policy before it releases a signature share. The on-chain half (validator, hook, registry) was done in T-1.3, T-2.2 and T-2.4. Everything is local; nothing was run on Base Sepolia, and the enclaves are still development processes with simulated attestation.

## What changed in practice

An enclave no longer signs a bare 32-byte hash. The coordinator now sends the whole user operation with every share request. The enclave recomputes the EntryPoint v0.8 operation hash itself, refuses if it differs from the hash it was asked to sign, and then checks the operation against a session policy it holds in sealed storage. An enclave with no policy signs nothing. There is no code path that signs without an authorizer: `EnclaveDependencies` requires one.

## Design decisions (please review)

1. **The enclave computes the hash.** `domain/user_operation_hash.py` reproduces the EIP-712 hash of EntryPoint v0.8.0 (domain `ERC4337`/`1`, chain id, EntryPoint address) with a pure-Python Keccak-256 (`domain/keccak.py`, because the standard library only has SHA-3). Tests compare it with hashes produced by the real EntryPoint in Forge for three operations (plain, with a paymaster, with init code) and with `cast keccak` across block boundaries.
2. **Call data is decoded strictly.** `domain/session_call.py` accepts only `executeAsSession(bytes32,bytes)`, the single and batch call types, the default execution type and an all-zero rest of the mode word, at most 16 executions. After decoding it re-encodes the result in canonical ABI form and refuses the operation unless the bytes are identical. A non-canonical encoding (gaps, shifted offsets, dirty padding, trailing bytes, dirty address words) is therefore refused, so the enclave and the account can never disagree about what the call data means. This is stricter than the hook, which is intentional: the enclave may refuse what the chain would accept, never the reverse.
3. **The policy mirrors the hook, plus the envelope.** `domain/session_policy.py` holds the same rules as `FintechPolicyHook` (allowlisted targets; the account, the zero address, the hook and the EntryPoint forbidden; native value counted against a native cap; capped ERC-20 `transfer` and `approve` only, exactly 68 bytes, no native value; approvals count like transfers) and adds checks the hook cannot make:
   - the sender is the policy's account, there is no init code, and the nonce key names the session validator;
   - the session time window (start inclusive, end exclusive) by the enclave's clock;
   - the paymaster must be in an allowlist if the operation has one;
   - an upper bound on the gas the operation can spend (`max fee x total gas limits`, paymaster limits included). The hook does not police gas, so before this check a compromised quorum could drain the account's EntryPoint deposit with huge gas limits.
4. **Each enclave keeps its own rolling-window ledger.** `application/spend_ledger.py` records the amount of every operation the enclave authorises, per asset, in sealed storage. A new operation is refused if the live events plus the new amount exceed the cap, or if 32 events are live. Events stop counting after exactly the window length. A retry of the same operation hash is not counted twice. The ledger counts what was signed, not what landed on chain, so it can only be stricter than the hook. The refusal is reported before any share exists.
5. **The policy is issued once.** The coordinator token can install a policy through a new `/policy` route; a second issuance is refused, and the policy is sealed so it survives a restart. There is no route to change or delete it. Changing the policy means provisioning new enclaves, which is the same ceremony as a new session key (R-NEW-5).
6. **A refusal burns the nonces.** The enclave pops its nonces before authorising, as before, so a refused request cannot be retried with the same commitments.
7. **Removed script.** `scripts/sign_with_local_enclaves.py` signed an arbitrary hash through the enclave processes. That is exactly what this task forbids, so I deleted it. `scripts/sign_session_hash.py` signs with the public FROST test vectors and does not touch the enclaves; it is unchanged.
8. **Drill signing paths.** The drill now has two ways to get a quorum signature: through the enclaves (all legitimate operations) and `compromised_quorum_signed`, which reads two shares from the sealed storage of nodes 1 and 2 and signs in-process. The second models a compromised quorum and is used only where the drill must show that the hook still refuses what the enclaves would never sign (plain `execute`, the self-call, the over-cap spend).

## Evidence

- Python: 281 tests pass, ruff, ruff format and mypy `--strict` (source and tests) clean. New tests cover Keccak, the hash vectors, the strict decoder (22), the policy (28), the authorizer and ledger (16), in-process quorums with enforcing enclaves, the HTTP policy route and operation wire form, and real enclave processes (a policy installed once, a bare hash refused, the policy and the ledger surviving a process restart).
- Mutation checks, each caught by at least one test: the hash comparison skipped; a missing operation accepted; the node not calling the authorizer; forbidden targets, the nonce key, the paymaster and the gas bound ignored; the session end made inclusive; the ledger cap ignored; the window expiry off by one; the outer and the batch canonical-encoding checks removed (the batch one first survived, so four tests with gaps and shifted offsets were added); approvals refused; a second policy accepted.
- Drill (`scripts\run-local-drill.ps1`), now 22 checks, two consecutive runs: the owner issues the policy to the three enclaves and a second issuance is refused; eight violations are refused by the enclaves, each for its own reason (a bare hash, a hash that is not the operation's, a target outside the allowlist, a value over the cap, a call to the account itself, the plain `execute` entry point, a foreign paymaster, excessive gas); the legitimate quorum operation still passes the bundler and executes through the hook; after 1 ETH was signed, one more wei is refused by the enclave ledgers; the hook-level checks from T-2.2 still pass with the compromised-quorum signer. The earlier checks, including the I-2 revocation and the I-7 recovery, still pass. With the node's authorizer call removed, the drill fails at "enclaves refuse every operation outside the policy" (`the enclaves signed: no operation, only a hash`).
- Intermittent test failure fixed: `tests/adapters/test_http_enclave.py` failed in roughly one of three full runs since T-2.2. The HTTP server answered 401, 404 and 413 without first reading the request body, so on Windows the client sometimes got a connection reset instead of the reply. The server now reads a body of up to 64 KiB before replying. Several full runs and repeated runs of that file passed afterwards.

## Risks and limits

- **The policy is installed by whoever holds the coordinator token.** In production the policy should be signed by the owner key and the enclave should verify it against the account's on-chain `signer()`; this is not built. A compromised coordinator could provision a new enclave set with a wider policy, but not widen an existing one.
- **The enclaves are development processes.** Attestation is simulated and nothing proves the code that runs is the code reviewed. The policy check protects against a compromised agent process, not against someone who controls the enclave host and its sealed storage.
- **Each ledger is local.** Enclaves 1 and 2 may have signed operations that enclave 3 never saw, so a later quorum of 1 and 3 is judged on a lower figure by enclave 3 and a higher one by enclave 1. A quorum needs both to agree, so the strictest member decides, but the figure is not the same everywhere. The hook on chain remains the authority.
- **The ledger counts signed, not landed operations.** An operation that was signed and never submitted still uses up cap until its window expires. An operation signed in a quorum that then failed to aggregate is counted once (retries are deduplicated by hash).
- **Clocks.** The time window and the rolling window use the enclave's clock, the hook uses block time. A skewed clock can make the enclave stricter or looser than the chain by the skew, within the 24 hour window; the validator still enforces the TTL on chain.
- **No recipient allowlist for tokens, and no minimum-received or sandwich check.** Same as T-2.2; they need trade intent or a price source. The enclaves also do not screen sanctions: only the on-chain hook does (`docs/T-2.3-sanctions-screening.md`).
- **Parser differentials are closed by strictness, not by proof.** The canonical re-encoding makes the decoder refuse anything ambiguous, and 22 tests cover the known malformed shapes, but there is no fuzzing against the Solidity decoder.
- **Gas bound is a configuration value.** It is 0.1 ETH in the drill; a production figure needs real gas data (T-1.8 and T-V1).
- **`approve` counts toward the window but there is no allowance tracking.** An allowance already granted to an allowlisted target is only bounded on chain by the hook's balance check.
- **Not exercised:** Base Sepolia, a rule-enforcing bundler, real attestation, ERC-7562 behaviour of anything new (the enclave work is off-chain).

# T-2.6 — semantic decoder for session-policy approval

2026-11-17. Scope is R-NEW-3: the screen where the user approves an agent's session policy, with no unlimited-approval path (ADR-001 §4, ADR-002 §3 step 1; basis `01.06` and research PDF §3.2). It is a pure Python library plus a plain-text renderer. There is **no graphical UI**, and nothing yet calls it to sign a grant (that is T-2.7).

## What changed in practice

`describe_policy` turns a `SessionPolicy` into an `ApprovalScreen`, and `render_text` prints it. The user sees, in plain words and exact amounts:

- **What the agent may do**: for each asset, "transfer or approve X to any address, up to N per rolling window" (approvals count against the same cap); for native currency, how much can be attached to calls to the allowed contracts; for each allowed contract, "call any function, with any data" and an explicit statement that the policy does not limit which functions.
- **Limits**: the cap per window **and** the most that could be spent over the whole session (cap times the number of windows the session spans, rounded up), the gas cost limit per operation, the sponsoring paymasters, and start and end in UTC with the session length.
- **What the agent can never do**, a caveat that allowed contracts can still use allowances the user gave them earlier, and a line that the user can end the session with the owner key alone.
- **Specific warnings**, one per concrete risk, not a generic one.
- **A policy fingerprint** (SHA-256 of the canonical policy, first 128 bits shown).

No raw calldata or hex payload is shown, and there is no "I accept the risks" button text: approval is `approve(screen, Acknowledgement)`, which succeeds only if the acknowledgement carries the screen's exact digest and **exactly** the warning keys the screen raised.

## The unlimited-approval path is closed in four ways

1. A cap at or above 2^128 is refused (`ApprovalRefusedError`). No real token has a supply near that; a policy built from `uint256 max` cannot be approved.
2. A token known to the catalog that is allowed as a **target** without a cap is refused. This is the real unlimited-approval route: an allowlisted token contract can be called with any data, including `approve(spender, max)`.
3. A target that is not in the catalog is flagged with a specific acknowledgement ("if it is a token, the agent could approve unlimited spending through it"), since the decoder cannot know what it is.
4. `narrow` lets the user lower caps, drop assets or targets and end the session earlier. It cannot raise a cap, add anything or extend the end, so the "options to limit" the workshop asks for cannot be used to widen. The narrowed policy gets a new digest and must be presented and acknowledged again; an acknowledgement of the old digest is refused.

Also refused: a session that has already ended, and one longer than `maximum_session_seconds` (default 30 days; a deployment parameter, not a protocol constant).

## Design decisions (please review)

These were not fixed by the plan, which gives only "Approval UI showing cap, allowlist, TTL and permitted actions".

1. **The decoder describes the policy, not the calldata.** In this design the human decision is the policy (ADR-002), so that is what is decoded. Decoding individual UserOperations for later review is not built.
2. **Token names are never taken from chain or from the policy.** A `DisplayCatalog` supplies symbol, decimals and contract labels. Symbols must be 1 to 12 letters or digits, labels short plain ASCII text, and catalog addresses lowercase, so a name cannot carry invisible characters or spoof layout. The address is always shown next to the symbol. An asset missing from the catalog is shown in **raw units**, as "unknown token", and needs an acknowledgement.
3. **The thresholds are parameters** (`ApprovalLimits`): 2^128 for "unlimited", 7 days for "long session" and 30 days for the maximum. I chose them; no project document gives values.
4. **Honesty about the allowlist.** The on-chain policy does not restrict functions or token recipients on allowed contracts and tokens (T-2.2, T-2.1). The screen says so rather than hiding it, including "to any address" for token transfers.
5. **Whole-session maximum is an upper bound.** It assumes the full cap is spent in every window the session spans. Actual rolling-window behaviour cannot exceed it.

## Evidence

- 45 new tests (Python total 428 passing). `ruff`, `ruff format` and `mypy --strict` are clean on source and tests.
- About 30 mutation checks, each caught by at least one test and then reverted. One survived at first (the "does not limit which functions" statement) and led to a new assertion.
- Sample output for the test policy (labelled contract and token, 33-minute session):

```
APPROVE AN AGENT SESSION

Ends:     1970-01-12 14:03:20 UTC  (33 minutes 20 seconds)

  - Transfer or approve USDT (0xe5e5...e5) to any address, up to 1,000 USDT per rolling 1 day. Approvals count against the same cap.
  - Call any function, with any data, on DeFi Yield Vault (0xd4d4...d4). The policy does not limit which functions.
The agent can NEVER: change its own limits; send an unlisted token or exceed a cap; act after the end time.
Please read before approving:
  ! Native currency can be attached to calls to the allowed contracts.
```

## Risks and limits

- **No graphical UI, and no user study.** The workshop's question is whether a novice understands the screen. That was not tested with anyone. The wording is mine and unreviewed by a designer or a legal reviewer, and it is English only.
- **Wired only into the local rotation ceremony (T-2.7).** There the screen is acknowledged by a scripted stand-in for the user and the owner key signs the batch; the check that the installed key and window are the approved ones is done after the fact (`docs/T-2.7-session-rotation.md`). No real user interface signs anything. Until one does, the digest binding proves nothing on its own.
- **The catalog is the trust root for names.** If the catalog is wrong or tampered with, the screen is wrong. Its provenance (who curates token lists) is not decided.
- **Unknown contracts remain a judgement call.** A contract that is not in the catalog is only flagged, and a user may acknowledge it.
- **Prior allowances are invisible.** The screen cannot see allowances the user already gave to allowed contracts, so it states the caveat in general terms only.
- **Warning fatigue is not measured.** Each warning is specific, but a policy with many unlabelled targets would need many acknowledgements.
- **Time is shown in UTC only,** and the sample date above is the test fixture's.

## Update (T-5.2)

The screen now has two modes. For an ordinary policy it is unchanged. For a payments-only policy it states that no call data is attached, that approvals are impossible, and that only the listed payees can be paid; it lists those payees and requires an acknowledgement for each one that the token list cannot name. See `docs/T-5.2-payment-guardrails.md`.

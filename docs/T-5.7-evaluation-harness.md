# T-5.7 — the evaluation harness

2026-11-21. Seventh task of the agent-factory program (`docs/agent-factory-program-plan.md`). A candidate is now **judged before anyone is asked to approve it**: seven checks on what it is, seven scenarios on what it does, a hard promotion gate, and the result written to the provenance chain before the owner sees a screen. No contract changed.

## What changed in practice

**The scenarios run the real enclave-side check.** `application/simulated_settlement.py` implements the runtime's two ports — balances and the intent sink — over `PolicyAuthorizer`, the same object an enclave runs: it rebuilds the session operation the signing path would build, hashes it, and asks the authorizer to authorise it against the derived policy and a real spend ledger. A scenario result therefore means *the enclaves would have refused this*, not *our copy of the rule refused this*.

**Seven scenarios** (`application/agent_evaluation.py`), each driving the candidate's own runtime:

| Scenario | What it shows |
|---|---|
| `pays-an-approved-payee` | the agent can do its job at all |
| `pays-once-on-a-retry` | the same key twice moves money once |
| `refuses-an-unapproved-payee` | a stranger is refused and nothing moves |
| `refuses-above-the-cap` | the per-window cap binds |
| `refuses-above-the-balance` | the funded budget binds |
| `refuses-cap-splitting` | two payments that together breach the cap: the second is refused |
| `refuses-after-the-session-ends` | the TTL binds |

**Seven checks** on the candidate and its derived authority: it can check a retry (it has `get_payment_status`), its payees are few, its caps are below the unlimited threshold, its session spans few rolling windows, its authority is payments-only with payees, and the generation was inside the time and cost budgets.

**A hard promotion gate** (`application/agent_promotion.py`). `promote` refuses unless the report is for *this* candidate's digest, the report passed, and the approval screen can be built. So a candidate that passes evaluation but fails the T-2.6 screen is still refused, and a report cannot be carried across to a different candidate.

**The drill evaluates before approving.** Provisioning now generates, derives, **evaluates**, records the evaluation, promotes, has the owner approve the promoted screen, and installs. The provenance chain holds five events per agent: generated, derived, evaluated, approved, installed.

## Deviations from the plan

1. **ADR-004's case bank does not apply.** The plan says the scenario bank is "seeded from ADR-004's case bank". I read it: its cases are S-1 buy-and-hold, S-2 mean reversion, S-3 momentum, S-4 periodic rebalancing and S-5 a multi-agent portfolio pipeline — all for the Phase 4 research agent, with no payment case among them. The payment bank here is new. What I took from ADR-004 is its *structure*: named scenarios, each with an expected outcome and a documented reason to exist.
2. **The adversarial suite feeding T-V3 is only partly here.** The generation-side injection suite lives in T-5.6 and the policy-violation attempts are the scenarios above. What is missing is an adversarial suite against a *model-driven decider*, because there is no model-driven decider — the scripted one ignores text, so feeding it a poisoned tool result proves nothing. That work belongs with the model adapter and with T-V3.
3. **Latency is a smoke budget, not a measurement.** The harness times its own simulated run (five seconds by default). It says nothing about on-chain or signing latency, which is still R-MET-3 and T-V1.

## Design decisions (please review)

1. **Evaluation reuses `PolicyAuthorizer` rather than re-checking the rules.** This is the whole value of the harness: the scenarios cannot drift from the enclaves, because they *are* the enclaves' check. The only simulated parts are the balances and the clock.
2. **Checks and scenarios are one report with one verdict.** `passed` is "no failure anywhere", and `failures` names each one, so the promotion refusal tells the owner exactly what was wrong.
3. **A report is bound to a candidate digest** and the gate compares it with the presentation's definition, so an old report cannot be attached to a new candidate.
4. **The rubric's numbers are mine:** at most 8 payees, at most 2 rolling windows per session, 5 seconds, 250,000 cost micros. No project document sets any of them. The window limit comes from the T-5.4 finding that a session crossing a window boundary doubles the worst case.
5. **The runtime takes the definition, not the approval.** Writing this task showed that `RuntimeContext` only ever used `approved.definition`, and evaluation would have had to fabricate an `ApprovedAgent` to run a candidate that is **not yet approved** — a lie in the type. The context now holds the definition, so an unapproved candidate can be run honestly.

## Mapping to the acceptance criteria

| T-5.7 acceptance criterion | Where it is proven |
|---|---|
| A deliberately bad candidate (over-wide payees, missing idempotency, unbounded cap) is refused promotion | `test_a_candidate_that_cannot_check_a_retry_is_refused`, `test_a_candidate_with_too_many_payees_is_refused`, `test_a_candidate_with_an_unbounded_cap_is_refused`, and `test_a_failing_candidate_is_never_promoted`; in the drill, "a candidate that fails evaluation never reaches an approval" |
| A candidate that passes evaluation but fails the T-2.6 screen is still refused | `test_a_candidate_the_approval_screen_refuses_is_never_promoted`, which passes evaluation and then presents the candidate after its session has ended |
| Evaluation results are attached to the provenance record before any human sees the candidate | The `EVALUATED` entry is written before `promote` builds the screen; the drill's binding check requires the five events in order |

## Evidence

- **Python: 766 tests pass** (742 before, 16 for the harness and 8 for the settlement). `ruff`, `ruff format` and `mypy --strict` clean on source and tests. Solidity is untouched at 218.
- **Drill: 37 of 37** (36 before), on two consecutive runs of the final code. The new check strips the status tool from a freshly generated candidate, evaluates it, and shows promotion refused with the harness's own words — *a payment agent needs get_payment_status to know whether a retry already paid* — with nothing written to the chain and the agent's cap and payee on chain unchanged.
- **Mutations: 24 at unit level, 23 caught.** The one survivor is reported below.
- **Two drill-level mutations**, both caught. Dropping the provenance record of the evaluation leaves the chain with four events instead of five, and the binding check lists what it found; relaxing the rubric so an agent no longer has to be able to check a retry lets the deliberately crippled candidate through, and the drill reports that *a candidate without the status tool was evaluated as sound*.

### What the mutations taught me

Four mutations survived the first pass, and three of them exposed a real gap: **every failure test failed a *check*, and none failed a *scenario***, so nothing proved that a failing scenario reaches the verdict at all. The fix was a test that evaluates an agent with no paying tool, which also surfaced something worth knowing:

> A crippled agent **passes** the refusal scenarios. An agent that cannot pay anyone trivially refuses to pay a stranger, refuses to exceed its cap, and refuses after its session ends. Its score is 7/7 checks and 4/7 scenarios, and only the three scenarios that require it to *do* something fail.

That is a limitation of negative scenarios in general, and it is why the bank has positive ones. The score string now appears in a test, so the counting cannot drift either.

**The remaining survivor:** in `refuses-an-unapproved-payee`, the conjunct `settlement.received(payee) == 0` can be removed without any test noticing. Falsifying it requires a *second* defect — the runtime paying an identifier it never resolved, or the settlement crediting a payee it never authorised — and both have their own tests. I kept the assertion rather than trade a real belt-and-braces check for a tidier mutation score.

## Risks and limits

- **The scenarios judge the authority, not the judgement.** With a scripted decider they test what the candidate's limits permit, not whether a model would behave. Nothing here can tell a sensible agent from a plausible-looking one.
- **The simulation is not the chain.** Balances and the clock are in memory; gas, the bundler, the hook's own checks, sanctions screening and the ERC-7562 rules are not simulated. The drill still covers those separately.
- **The rubric is six thresholds and a judgement call.** None is calibrated against anything, and a candidate can pass every check and still be wrong for the business task.
- **Negative scenarios can be passed by doing nothing** (above).
- **Latency and cost are smoke budgets.** The time budget measures the harness, and the cost figure is the generation cost the proposer reported, which a real adapter must measure from the provider instead.
- **No adversarial suite against a model-driven decider**, because there is none to attack (deviation 2).
- **The report is in memory** and only its summary reaches the provenance chain: the score, the duration, the cost and the candidate digest, not each finding. Replaying a report later would need the findings stored too.
- **Still local:** simulated attestation, development keys, Alto with safe mode off, no Base Sepolia, unaudited.

# T-2.4 — ERC-7484 module registry and install gate

2026-11-17. `contracts/FintechModuleRegistry.sol` (ERC-7484 registry), `contracts/interfaces/IERC7484Registry.sol`, and an install gate in `FintechModularAccount`. Scope is DC-5 and R-P2-3: a module cannot be installed unless a trusted attester has attested that module at that address. Everything is local; nothing was run on Base Sepolia.

## What changed in practice

`installModule` on the account now asks the registry first, for every module type including the policy hook itself. An unattested module, a module whose attestation was revoked or has expired, a module attested for a different type, and a module whose code at that address differs from what was attested are all refused, and the install changes nothing. Uninstalling never consults the registry, so the owner can always remove a module (I-2).

## Design decisions (please review)

These were not fixed by the roadmap. I chose the simplest option that is sound.

1. **The registry is our own contract that implements the ERC-7484 interface.** It has all seven functions of the spec, plus `attest`, `revoke` and `attestationOf`. It has no owner: anyone can attest, and each account decides which attesters count. The account only calls the external-attester form `check(module, moduleType, attesters, threshold)`, which any ERC-7484 registry has, so the registry can be swapped for another one without changing the account code.
2. **Where the spec leaves room, the registry is stricter.**
   - An attestation binds the module's code hash. A check passes only while `extcodehash` of the module equals the hash recorded at attestation time. The same bytecode at another address is not attested.
   - A revocation by any attester in the checked set makes the check revert, even if the threshold is otherwise met (the spec says MUST revert if any attester revoked). A revocation is permanent: the same attester cannot attest that module again, so the attester must use a new address for a corrected attestation.
   - A threshold of 0 is refused, because it would accept every module. The attester set must be non-empty, at most 16, sorted, unique and without the zero address.
   - An attestation covers a set of module types stored as a bit mask, so one module can be attested as more than one type. If an attestation that is otherwise valid does not cover the requested type, the check reverts (the spec says MUST revert on a type mismatch).
   - Expired attestations do not count. At the exact expiry second they still count.
3. **The account stores its own attester policy.** At creation the factory gives each account one trusted attester with a threshold of 1 (both are constructor arguments of the factory, stored as immutables). The owner can replace the set with `setAttesterPolicy`, which only the EntryPoint or the account itself can call. A session-class operation cannot reach it: it is rejected by the selector gate, and a session `executeAsSession` self-call is refused by the policy hook (tested with a valid quorum signature for the first case). I kept the policy in the account instead of in the registry because account-creation validation can then read only its own storage and immutables (ERC-7562), and because the registry's per-account lists are not needed. The registry still implements `trustAttesters` and the internal-attester checks, as the interface requires, but the account does not use them.
4. **The registry address is an immutable of the account implementation.** A malicious owner key or module cannot point an account at a registry that approves everything. The cost is that changing the registry needs a new implementation and factory; existing accounts keep their old registry.
5. **The gate is install-time only.** The spec says the registry should be queried before or during the transaction in which a module is first called, and that checking on execution is optional. I did not check on every use because a use-time check during UserOperation validation would read registry storage keyed by module and attester, which ERC-7562 does not allow for an unstaked entity. Revoking an attestation therefore stops new installs but does not disable a module that is already installed. Test `testRevokingAnAttestationDoesNotStopAnAlreadyInstalledModule` records that behaviour on purpose.
6. **The check runs before the module's own `onInstall` and before the hook wrapper.** An unattested module never runs any code in the account's context.
7. **Changing the factory arguments changes account addresses.** The account address depends on the implementation address, which now embeds the registry. The fixed session signatures in `test/FintechModularAccount.t.sol` were regenerated with `scripts/sign_session_hash.py`.

## Mapping to the roadmap items it remediates

| Item | Remediation |
|---|---|
| DC-5, R-P2-3 (every installed module is attested before installation completes) | `_installModule` calls the registry for every module type, including the policy hook, the validator and the recovery module |
| A-5 residual (no ERC-7484 check in the installable module path) | The check is in the account's own install path, not in an optional module |
| Plan sequencing (T-2.4 before module installation) | The local pipeline now attests the validator, recovery module and hook before it installs them |

## Evidence

- Forge: 185 tests pass (30 for the registry, 14 new for the account gate, the existing suites updated for the new factory and the regenerated signatures). `forge fmt --check` clean.
- Mutation checks, each caught by at least one test and then reverted: removing the registry call from `_installModule`; leaving `setAttesterPolicy` open to anyone; ignoring the code hash; ignoring revocation (two tests); ignoring expiry; allowing a threshold of 0 (two tests).
- Drill (`scripts\run-local-drill.ps1`), now 19 checks: a generated attester key attests the validator, recovery module and hook after deployment, and the first three installs pass the gate. A second, unattested instance of the recovery module is then refused by the registry with `AttestationThresholdNotMet`, and an owner operation that tries to install it is included on chain and changes nothing. After the attester attests it, the same operation installs it (the control), and an owner operation uninstalls it. After the attester revokes, the registry refuses with `AttestationWasRevoked` and the install changes nothing again. The earlier 17 checks, including the I-2 revocation and the I-7 recovery, still pass.
- The first version of the drill check was vacuous. I removed the gate from the account and the drill still passed, because the directly included install ran out of call gas (300k) even when the module was attested. I added the positive control above and a higher call gas limit for installs. With the gate removed the drill now fails at that check (`installed state is True, expected False`).
- Python: 192 tests pass, ruff, ruff format and mypy `--strict` clean.

## Risks and limits

- **No attester has been identified (IG-8).** Locally a generated key attests, which proves the mechanism and nothing about trust. In production the gate is only as strong as the audit behind an attestation (T-V2), and the registry and the changed account are unaudited. ERC-7484 is a Draft.
- **A revocation does not unwind installed modules.** If an attester revokes, the owner has to uninstall the module. Use-time checks need a storage layout that ERC-7562 allows, or a staked entity, and are not built.
- **An attestation binds the code hash, not behaviour.** A proxy or upgradeable module keeps its code hash when its implementation changes, so attesters must not attest proxies. Self-destructing modules are not a concern after Cancun except in the creating transaction, but this was not tested.
- **The owner is the root of trust.** The owner can change the trusted attesters and can then install anything those attesters attest. The gate protects against unattested code, not against an owner who trusts a bad attester.
- **A single attester with a threshold of 1 is the default.** A compromised attester key could attest a malicious module for every account that trusts it, although installing it still takes an owner-signed operation. Use a threshold of 2 or more in production. The default is a factory immutable, so changing it needs a new factory.
- **An invalid attester policy blocks installs.** If the owner sets an empty or unsorted set, installs revert until the owner fixes it. Uninstalls and all other operations are not affected (tested).
- **Registry choice is fixed per implementation.** Existing accounts cannot move to another registry.
- **ERC-7562.** Account creation reads only immutables of the factory and writes only the account's own storage. A rule-enforcing bundler was not used (safe mode is off locally), so acceptance by a public bundler is not shown.
- **Gas of the check was not measured.** It adds one external view call to each install.
- **One pytest run in three fails a `tests/adapters/test_http_enclave.py` test now and then.** It failed with and without a drill running before it, a different test each time, and passed on re-run (192 passed). Those files are not part of this change and I did not find the cause.

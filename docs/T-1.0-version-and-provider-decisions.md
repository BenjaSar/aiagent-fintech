### Evaluation against the architecture — DECIDED by user 2026-11-16, conditional on endpoint tests

Adopted as written. Each provider remains conditional on passing the v0.8.0 endpoint test; a provider that fails is replaced under the same ports, not worked around.

Selection criteria taken from the plan: v0.8.0 support confirmed by `eth_supportedEntryPoints` (§1.2); gas sponsorship only, no token authority (I-6); revocation and recovery must work with all company infrastructure offline (I-2, I-7, Phase 1 exit gate), so the owner path cannot depend on the company's paymaster or bundler; latency measured on this stack, not assumed (T-V1, R-MET-3, R-MET-4).

1. **Provider-independent ports.** Define a bundler gateway and a paymaster gateway as ports in the application layer, with each vendor as an infrastructure adapter. Bundler calls stay on the standard ERC-4337 RPC methods so a provider can be swapped without touching use cases. This also lets the I-2 drill run through a bundler the company does not operate.
2. **Bundler: Etherspot Skandha primary, Candide Voltaire secondary, both conditional on passing the endpoint test.** Skandha is the only option with an explicit v0.8 plus Base Sepolia statement. A second, independent bundler gives the I-2 drill a path that does not share an operator. Rundler and Alto stay out until a first-party source confirms v0.8. No latency figure is claimed: the 120–200 ms execution budget covers submission, and inclusion time on Base depends on block timing, which T-V1 must measure.
3. **Paymaster: hosted sponsorship for the testnet prototype, a self-deployed signer paymaster as the production target.** A hosted sponsor adds no contract surface to audit while the design is still moving, but only if it passes the same v0.8 test; Coinbase CDP's Base Sepolia sponsorship is the candidate, and its EntryPoint version is unconfirmed. For production, a self-deployed signature-based paymaster keeps I-6 provable and removes a vendor from the sponsorship path. Its signing key sponsors gas only and must be separate from the FROST session key. Costs: a new on-chain contract that needs the T-V2 audit, and an owner path that must work without it. The OpenZeppelin `PaymasterSigner` is a starting point, but its page shows examples built on the v0.9 ABI (compatibility with v0.8 unverified) and an "Unaudited code" warning; the v0.8.0 repo tag has no sample verifying paymaster to use instead.
4. **Excluded for now:** Circle Paymaster (pulls ERC-20 from the account, conflicts with I-6), base-org paymaster (targets the v0.6 EntryPoint), Coinbase VerifyingPaymaster (v0.7).

## Audit finding

At tag v0.8.0 the repository's `audits` folder holds three PDFs: an incremental audit dated Feb 2023, an incremental audit report dated Feb 20 2024, and a Spearbit review dated Mar 2024. All predate the v0.8.0 release (26 Mar per the releases page), and I have not opened them. Nothing read shows that v0.8.0 itself was audited. The plan's requirement of a canonical audited deployment (§1.2) is therefore **not established** for v0.8.0. Choosing v0.7.0 or v0.6.0 would not necessarily fix this; their coverage was not checked either. DECIDED by user 2026-11-16: keep v0.8.0 with this gap on record as an accepted risk. The gap stays visible against §1.2 and should be revisited if a v0.8 audit is published or before any production deployment.
